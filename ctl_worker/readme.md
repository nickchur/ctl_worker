# CTL (Change Tracking & Loading) — Система управления ETL-процессами в Airflow
*2026-09-04 14:08 MSK · v1.14 · Nick Churkin · [NSChurkin@sber.ru](mailto:NSChurkin@sber.ru)*

---

## 📋 Обзор

Данный проект реализует интеграцию **Apache Airflow** с системой управления ETL-процессами **CTL (Change Tracking & Loading)**.  
Он обеспечивает автоматизированное управление загрузками данных из внешних источников в хранилище (Greenplum) через динамически генерируемые DAG'и.

Система поддерживает:
- Динамическую генерацию DAG'ов под каждый workflow
- Событийную оркестрацию через Dataset'ы
- Управление retry-логикой с автоматической задержкой между попытками
- Мониторинг SLA и автоматическую обработку ошибок
- Централизованное управление конфигурацией через Airflow Variables

## 🏗️ Архитектура

Система состоит из нескольких модулей, отвечающих за различные аспекты жизненного цикла ETL:

| Компонент | Файл | Назначение |
|-----------|------|------------|
| **Worker** | `ctl_worker.py` | Динамически генерирует по одному DAG'у на каждый workflow: инициализация загрузки, выполнение SQL в GP, публикация статистики, финализация и retry. |
| **Sensor** | `ctl_sensor.py` | Каждую минуту опрашивает CTL API, фильтрует загрузки со статусом `RUNNING`/`TIME-WAIT`/`EVENT-WAIT` и запускает нужные DAG'и. |
| **Loader** | `ctl_loader.py` | Выгружает из CTL метаданные (workflows, сущности, события, категории) и кладёт в S3 + Airflow Variables. |
| **Monitor** | `ctl_monitor.py` | Анализирует активные загрузки: проверяет SLA, переводит зависшие в `Aborted`, инициирует retry и перезапуск. |
| **Events** | `ctl_events.py` | Опрашивает события CTL и публикует Airflow Dataset'ы `CTL/{profile}/{eid}/{ename}` для запуска зависимых DAG'ов. |
| **Config** | `ctl_config.py` | Инициализирует и сохраняет всю конфигурацию системы в Airflow Variable `ctl_config`; защищена PIN-кодом. |
| **Simulator** | `ctl_test.py` | Симулятор нагрузки: события сущностей, Dataset-сигналы или случайные запуски DAG'ов (ключ `simulator`). Существует только на DEV, IFT и PSI. |
| **Checker** | `ctl_checker.py` | Ручная диагностика CTL API: произвольные HTTP-запросы (GET/POST/PUT/DELETE) с шаблонами URL (`{lid}`, `{wid}`, `{eid}`). |
| **YAML Export** | `ctl_yml.py` | Экспортирует конфигурацию CTL (категории, сущности, workflows) в YAML-файлы в S3 для бэкапа и IaC. |
| **TFS → S3** | `ctl_tfs.py` | Перемещение файлов из TFS в S3: по расписанию (`tfs_sensor`) и по Kafka-событию (`tfs_kafka`) с отправкой квитанции `TransferFileCephRs`. |
| **Test Conn** | `ctl_test_conn.py` | Непрерывный мониторинг доступности подключений (CTL, Greenplum, PostgreSQL, S3) с экспоненциальным backoff. |

## 🔧 Основные компоненты

### `ctl_worker.py` — Рабочий процесс загрузки

По одному DAG `CTL.{wf_name}` на каждый активный workflow.

**Пайплайн задач:**
1. `run_prm` — Инициализация: создание загрузки в CTL, извлечение параметров из триггера.
2. `run_tfs` *(опционально)* — Загрузка CSV-файлов из S3 в Greenplum (если `wf_tfs_in`).
3. `run_exe` — Выполнение SQL-процедуры `pr_swf_start_ctl()` в Greenplum, сбор метрик.
   Контракт вызова (входной JSON, подстановки `$lid$`/`$try$`, коды `res`) и сами
   скрипты GP — в [`GP/readme.md`](../GP/readme.md). Функция неидемпотентна,
   поэтому у таска `retries=0`, а повторы делает CTL через `TIME-WAIT`.
4. `run_out` *(опционально)* — Экспорт результата в TFS (если `wf_tfs_out`).
5. `run_end` — Публикация Dataset'ов, обновление статуса в CTL, retry при необходимости.
   Итог попытки кладётся снимком в `ctl_done/` (см. ниже) — до ветвления на пропуск и
   падение, иначе как раз самые интересные исходы в хранилище бы не попали.

**Снимки загрузок в бакете CTL** (`edpetl-ctl`, срок хранения — правило бакета, 7 дней):

| Префикс | Что лежит | Кто пишет |
|---|---|---|
| `ctl_working/{lid}` | состояние **на вход в шаг**: проверка идёт в начале каждого, ключ перезаписывается | `ctl_chk_status` |
| `ctl_done/{lid}_{try}` | **итог попытки** после финализации: статус, лог результата, признак завершения, время пробуждения при TIME-WAIT. Номер — `try` из `wfp_retry` (счёт с 1; `0` — повторы у воркфлоу не настроены) | `run_end` |
| `ctl_loadings/{profile}/{id}` | снимки из списка сенсора (`/v5/api/loading/extended`) | `ctl_loading_load` |

Раскладка задана в одном месте — `ctl_loading_snapshot` (`plugins/ctl_core.py`). Итог
берётся из ответа финализирующего вызова, лишнего запроса к CTL нет; ответ непохожей формы
приводит к перечитыванию полной загрузки. Неудача сохранения исход не меняет: загрузка уже
финализирована в CTL, и красный таск после этого противоречил бы её статусу.

⚠️ `ctl_working/` читает сборщик фикстур эмулятора (`testbed/fixtures_from_cache.py`) —
поэтому итог живёт отдельным префиксом, а не рядом: иначе на стенде загрузки приезжали бы
завершёнными и сенсору было бы нечего брать.

**Особенности:**
- Динамическая генерация: 1 DAG на каждый не-архивный workflow.
- Триггеры: Dataset-событие, cron, `DatasetOrTimeSchedule`, AND/OR-условия.
- Retry с настраиваемой задержкой (`delay` + `add` на каждый повтор).
- HTML-отчёт отправляется в CTL если результат содержит поле `html`.

### `ctl_sensor.py` — Сенсор событий

**Функции:**
- Проверка подключений (CTL, Greenplum, PostgreSQL, S3) в `chk_conn`.
- Опрос CTL API каждую минуту (`ctl_add_get`), лимит 50 загрузок.
- Фильтрация по статусу: `RUNNING`, `TIME-WAIT`, `EVENT-WAIT`; только `alive=ACTIVE`.
- Проверка готовности: учёт `expire`, задержки retry, дубликатов.
- Запуск DAG'а через `trigger_dag` или Dataset-публикацию (если `dag_run='dataset'`).
- Обновление статуса загрузки в CTL на `RUNNING` с пометкой `WAIT-AF`.

**Дага нет.** `trigger_dag` берёт даг из `serialized_dag`, а UI показывает его по строке в
`dag` — поэтому даг бывает виден, но не запускается («missing from DagBag»). В этом случае
сенсор не падает трейсом `DagNotFound`, а разбирает причину (есть ли воркфлоу в
`ctl_workflows`, его `deleted`/`profile`, есть ли строки в `dag` и `serialized_dag`), пишет
её в заметку и пропускает загрузку. В CTL загрузка остаётся как была: вернётся даг —
поедет и она.

**Даг на паузе.** Тот же класс: запускать нечего. `trigger_dag` паузу не смотрит и создаёт
ран сразу в очереди, который не поедет никогда, — поэтому сенсор проверяет паузу заранее и
загрузку пропускает, называя её происхождение:

| Что в заметке | Что это значит |
|---|---|
| «поставил `<кто>` `<когда>`» | осознанное решение человека — видно по событию `paused` (веб) или `cli_dag_pause` (командная строка) в журнале метабазы |
| «рубильник тракта» | ключ `is_paused` в `ctl_config`: фабрика проходит по всем дагам профиля и ставит паузу через `update_dag_pause` — записи в журнале нет, потому что пишется прямо в `DagModel` |
| «записи в журнале нет» | либо пауза с создания (фабрика создаёт даг запаузенным, если воркфлоу не на расписании в CTL: `is_paused_upon_creation = not w['scheduled']`), либо её поставили кодом или через REST API |

Последние два происхождения по метабазе неразличимы, и заметка их не различает: честное
«одно из двух» лучше уверенно названной не той причины. Ошибиться здесь дорого — оператор
поверит «воркфлоу не на расписании», снимет паузу, а тракт был выключен целиком.

Обратный ключ тоже есть: `un_paused` в `ctl_config` снимает паузу со всех неархивных дагов
профиля — включая поставленную при создании. Это рубильник для человека, а не автоматика:
сенсор и монитор паузу не трогают ни в какую сторону.

**Паузу сенсор не снимает.** У воркфлоу, не стоящего на расписании в CTL, `get_schedule`
строит дагу **собственное расписание Airflow** — из `wf_tfs_in`, `wf_event_sched`,
`wf_time_sched` или `startCondition`. Снять паузу значит заодно включить это расписание, о
котором CTL не просил. Поэтому решение оставлено человеку, а наше дело — не делать вид,
что запустили.

Каждый такой пропуск пишется в журнал метабазы событием `ctl dag paused` — чтобы «сколько
раз за сутки» считалось запросом, а не поиском по логам (`check/log_events.py`). Пишется не
чаще раза в час на даг: сенсор ходит раз в минуту и статуса загрузки не меняет, так что без
потолка каждая ждущая загрузка давала бы 1440 строк в сутки. Запись обёрнута в try/except —
диагностика не должна ронять штатный пропуск. Загрузки, застрявшие в этом состоянии, монитор
показывает списком с возрастом (см. ниже, раздел монитора).

### `ctl_loader.py` — Загрузчик метаданных

Частота: по `loader_interval` (по умолчанию 15 мин).

**Сохраняет в S3 и Airflow Variables:**
- `ctl_profile` — метаданные профиля.
- `ctl_categories` — дерево категорий с именами родителей.
- `ctl_entities` — иерархия сущностей (ID → метаданные).
- `ctl_enames` — сопоставление ID → короткое имя сущности.
- `ctl_workflows` — нормализованные определения workflows (params, события, уведомления).
- `ctl_events` — расписание событий.
- `ctl_entity_events` — привязка событий к сущностям.
- `ctl_ue_events`, `ctl_prf_events` — история событий.

Изменения обнаруживаются по MD5-хэшу — лишние записи не создаются.

**Защита от усадки списка.** `ctl_workflows` — источник дагов для фабрики
(`ctl_worker.py`), а Airflow считает даг пропавшим, если очередной разбор файла его не
вернул, и удаляет строку из `serialized_dag` (`deactivate_stale_dags`). То есть короткий
список молча убивает даги. Поэтому:

- загрузчик не перезаписывает `ctl_workflows`, если CTL вернул пусто или меньше прежнего
  больше чем на `wf_shrink_pct` (в `ctl_config`, по умолчанию 10) — таск падает, прежние
  данные остаются в силе;
- рядом пишется `ctl_workflows_stat` (`count`, `eligible`, `md5`, `saved`) — счётчик, по
  которому фабрика сверяет то, что прочитала сама;
- фабрика при пустом или усохшем списке поднимает исключение на импорте: ошибка импорта
  оставляет уже сериализованные даги живыми, а «успешный» короткий разбор их уничтожает.

Счётчик пишется до сохранения: `load_obj_save` при неизменившихся данных бросает
`AirflowSkipException`, и всё, что стоит после него, не выполнилось бы никогда.

### `ctl_monitor.py` — Мониторинг

Частота: по `monitor_interval` (по умолчанию 15 мин), лимит 25 загрузок.

**Правила по статусу:**
- `ERRORCHECK` → `reRunned` 🔁
- `ERROR` + `abortOnFailure` → `Aborted` 🚫; иначе → `Completed` ✅
- `SUCCESS` → `Completed` ✅
- `TIME-WAIT` > 15 мин → `reStarted` ⚠️; иначе → `Skipped`
- `LOCK`/`LOCK-WAIT` > 5 ч → `reStarted` ⚠️
- `RUNNING` > 6 ч → `reRunned` (с логом SLA) 🚨

XCom из `ctl_monitor`: `{lid: {wid, wfn, sts, act, sch, ...}}` — передаётся в `ctl_action` для выполнения действия.

**Заметка «⏸️ Ждут снятия паузы».** Рядом со сводкой SLA монитор перечисляет загрузки,
которым **есть куда ехать прямо сейчас**, а даг на паузе, — с возрастом от последней смены
статуса. «Есть куда ехать» — это два признака: посчитанное действие (`New` — запустит
сенсор, `reRunned` и `reStarted` — перезапустит монитор) и `RUNNING` с пустым логом. Второй
признак и ловит типичного ждуна: CTL считает загрузку идущей, а воркер её не начинал —
сенсор пропустил запуск из-за паузы, писать лог некому. По действию такую не поймать,
монитор помечает её `Skipped` и оставляет сенсору. Выполняющаяся загрузка (лог `RUN`),
доигрывающая и спящая по таймеру в списке не появятся — иначе заметка кричала бы на
нормальную работу, а дежурный перестал бы её читать. Такая загрузка не поедет: сенсор её пропускает
(см. выше, раздел сенсора), а сама пауза снимается человеком. Без этой строки «загрузка
ждёт вторые сутки» видно только чтением логов сенсора минута за минутой — на снимке боевых
данных таких загрузок нашлось 28.

В заметку идут счёт и десяток старейших: она обрезается по `MAX_NOTE_LEN` (1000 символов),
и длинный список вытеснил бы записанные тем же тиком `Action` и `Status`. Полный список — в
логе таска. Даги, выпавшие из `ctl_workflows` (`is_active = false`), в список не берутся:
им не паузы ждать, а диагностики пропавшего дага.

**Таск `ctl_zombie` — санитар метабазы.** Идёт рядом с `ctl_action` и убирает то, что
планировщик объявляет зомби, но добить не может: колбэк зомби-кила исполняется в контексте
файла дага, а даг мог исчезнуть — воркфлоу выпал из `ctl_workflows`, и фабрика его больше
не строит. Тогда состояние не меняется никогда.

| Что убирает | Признак | Загрузка за раном |
|---|---|---|
| Зависший таск | `RUNNING`, а его `job` не зарегистрирован, не жив или не бился дольше порога | `ERROR` + `completed=false` |
| Осиротевший ран | `RUNNING` без единой живой задачи | `ERROR` + `completed=false` |
| Ран-призрак | `RUNNING` или `QUEUED` у дага, которого нет в `serialized_dag` | `ERROR` + `completed=false` |
| Ран у запаузенного дага | `QUEUED`, а даг на паузе | не трогаем |

За раном вида `sensor__<lid>_<попытка>_<дата>` стоит загрузка CTL, и вот тут исходы
расходятся. Ехать некуда — загрузка переводится в `ERROR` + `completed=false`, иначе CTL
считает её активной впустую. А пауза — это плановые работы, а не смерть: ран закрыть надо
(он всё равно не поедет, сенсор создаст новый), но загрузку трогать нельзя — снимут паузу,
и сенсор запустит её заново. Иначе ночное окно обслуживания дольше порога стоило бы нам
всех загрузок, которые в него попали. Тот же принцип сенсор применяет при `DagNotFound`:
«вернётся даг — поедет и она».

Живым считается ран, у которого есть задача в `running`, `queued`, `scheduled`,
`up_for_retry`, `deferred`, `up_for_reschedule` или `restarting`. Последние два важны не
меньше первых: сенсор в режиме reschedule между опросами лежит именно в
`up_for_reschedule`, и без него санитар добивал бы ждущий `tfs_wait` на шестом часе
суточного ожидания — вместе с собственным раном монитора.

Порог — `zombie_after` в `ctl_config` (по умолчанию 6 часов) и обязан быть больше
`exe_timeout`: длинный `run_exe` не бьётся чаще, чем работает. Ниже пяти минут порог не
опускается — таск падает с объяснением, потому что санитар с околонулевым порогом
закрывает живое. Порог применяется ко всем случаям: даг пропадает из сериализации и на
время сбоя разбора, а паузу ставят на время работ. Параметр формы **«Санитар: только
показать»** (`zombie_dry_run`) перечисляет находки, ничего не трогая, и показывает полное
их число рядом с потолком (`найдено 218, потолок 500`); первым запуском на новом контуре —
только так.

Два ограничения, о которых стоит знать. Возраст рана считается от его создания, а не от
момента паузы: узнать, когда даг запаузили, метабаза не даёт — наш код правит `DagModel`
напрямую и следа в журнале не оставляет. Поэтому пауза, поставленная поверх давно висящей
очереди, отдаёт эти раны санитару сразу. И радиус — вся метабаза, а не только `CTL.*`:
припаркованный ручной запуск дага из `tools/` или `check/` тоже будет закрыт через шесть
часов. Оба поведения осознанные: ран, который не поедет, очередь занимает одинаково,
кому бы он ни принадлежал.

Зачем это нужно: на alpha так накопилось 33 таска, самым старым — с апреля. Они держали
слоты `ctl_pool`, каждое объявление зомби дёргало `on_failure_callback` (за пять минут —
под тысячу вызовов и 33 МБ лога), а один ран-призрак давал 60 строк
«DAG ... not found in serialized_dag» в секунду.

### `ctl_config.py` — Управление конфигурацией

Запуск `@once` (ручной). Сохраняет конфигурацию в Airflow Variable `ctl_config`.

**Управляемые параметры:**
- Профиль и иерархия: `profile`, `root_category`, `root_entity`, `ue_category`.
- Подключения: `ctl`, `gp`, `pg`, `s3` (основной), `files` (edpetl-files), `tfs` (источники файлов).
- Таймауты: `task_timeout`, `exe_timeout`, `sla_time`, `gp_timeout`.
  `exe_timeout` — это `statement_timeout` сессии Greenplum, и он держится **на пять
  минут ниже серверного лимита**: сервер обрывает долгий запрос вместе с соединением,
  и логи с ошибкой записаться не успевают. Свой таймаут срабатывает раньше, ошибка
  попадает в лог и в письмо. Поднимать его выше серверного нельзя — см.
  [`GP/readme.md`](../GP/readme.md).
- Пулы и лимиты: `ctl_pool_slots`, `ctl_limit`, `ctl_days`.
- PIN-защита: сохранение требует совпадения `AIRFLOW__CTL_PIN` из `/vault/secrets/application`.

### `ctl_test.py` — Симулятор нагрузки

Режим задаётся ключом `simulator` в `ctl_config`, частота — `simulator_interval`.

**Режимы (`simulator`):**
- `off` (умолчание) — таск уходит в пропуск.
- `event` — создаёт значения событий сущностей через POST в CTL API. По умолчанию берёт
  сущности **чужих профилей** (`all_events` снимает фильтр), то есть изображает внешние
  системы, которых мы ждём. Поэтому только DEV.
- `dataset` — публикует Dataset-сигналы напрямую в Airflow.
- `trigger` — случайным образом запускает DAG'и воркфлоу через `trigger_dag`.

Учитывает загрузку системы (проверяет занятость пулов), игнорирует archive-категории.

⚠️ Запуск дага воркфлоу — это **настоящая загрузка в CTL**: `start_wf` в параметрах по
умолчанию истинный, поэтому `run_prm` доходит до `POST /v4/api/wf/{wid}/loading`, а CTL
шлёт письма по `statusNotifications`. Притворяться будет только выполнение и только там,
где разрешён `test_mode`, — это отдельный ключ.

**Запускаются только те даги, которые поедут.** `trigger_dag` состояние паузы не смотрит:
он создаёт ран сразу в `queued`, а планировщик запаузенный даг не разбирает — такой ран
висит в очереди навсегда. Симулятор без отбора целился ровно в них: фабрика создаёт даг
запаузенным, если воркфлоу не на расписании (`is_paused_upon_creation = not w['scheduled']`
в `ctl_worker.py`), а из выборки исключены как раз воркфлоу «на расписании и с единственной
загрузкой». На стенде (он поднят из снимка боевых данных) это 676 запаузенных дагов из 677. Поэтому кандидаты сначала
проверяются по метабазе — не на паузе, активен, есть в `serialized_dag`, — и в заметке
видно, сколько отсеяно. Счётчиков два, и это не педантизм: «не поедут N» — отсев по
метабазе, «не подошли по свойствам N» — воркфлоу нашего профиля, которые симулятору не
нужны (удалённые, архивные, со своим расписанием). Одним числом эти два ответа на «почему
запусков мало» неразличимы. Пустой отбор даёт пропуск, а не пустой запуск, а неудавшиеся
`trigger_dag` попадают в отдельную заметку — иначе «запустил 3 из 5» видно, а причина
только в логах таска. Дубль рана в отказы не идёт: загрузка поедет, воркфлоу остаётся
среди запущенных, но строка о нём видна отдельно — по построению `run_id` уникален
(собирается из `start_date` таска), так что дубль означает что-то неожиданное.

Выбор идёт без повторов: `run_id` внутри таска один (собирается из `start_date`), и
повторный выбор того же дага упирался бы в `DagRunAlreadyExists`.

### Контуры: где что работает

Контур берётся из `ENV_STAND`, при её отсутствии — из `ENVIRONMENT` (`env_stand()` в
`plugins/utils.py`). Списки контуров зашиты в код: контур — единственный признак, которым
нельзя управлять ни из `ctl_config`, ни из параметров воркфлоу в CTL.

| | DEV | IFT | PSI | PROM | пусто / неизвестный |
|---|:--:|:--:|:--:|:--:|:--:|
| DAG симулятора зарегистрирован | + | + | + | — | — |
| `simulator: event` (запись в CTL) | + | — | — | — | — |
| `test_mode` (фиктивное выполнение) | + | + | — | — | — |

Пустая переменная и незнакомое имя приравниваются к бою: переменная выставлена на всех
контурах, включая стенд (`ENV_STAND=DEV`), поэтому «не знаю, где я» — повод ничего не
подделывать.

**Тестовый режим (`test_mode`)** подменяет выражение воркфлоу на `pg_sleep` (верхняя
граница — `test_sleep`, по умолчанию 45 минут) и подставляет код результата по профилю:

| Профиль | Коды (веса) | Что проверяется |
|---|---|---|
| `ok` | `1` | только успешный путь |
| `ok-no` | `1` ×3, `0` ×1 | успех и «нет данных» |
| `ok-no-error` | `1` ×3, `0` ×1, `-1`, `-2`, `-7` | плюс ошибки, включая циклический повтор |

Подставленный код попадает в заметку `Result` вместе с именем профиля — тестовая `-7` не
должна быть неотличима от настоящей. Прежнее истинное значение ключа (`true`, `event`, …)
читается как `ok-no` с предупреждением в логе.

### `ctl_tfs.py` — Перемещение файлов из TFS

Содержит два DAG'а:

- **`tfs_sensor`** — опрашивает все `tfs-in`-источники из конфига по расписанию (по умолчанию каждые 5 мин). При обнаружении файлов копирует их в S3 и публикует `DatasetAlias("TFS/<profile>")`.
  Недоступный источник (нет бакета, нет прав, молчит шлюз) не закрывает остальные:
  причина пишется человеческой строкой («бакет … не заведён на коннекте …»), а не
  трейсом botocore. Если файлов не нашлось ни у кого и хоть один источник не
  опросился — таск падает с перечнем причин; если все источники живы и пусты — ждёт.
- **`tfs_kafka`** — триггерный DAG: читает `TransferFileCephRq` из Kafka, копирует указанные в XML файлы, затем отправляет квитанцию `TransferFileCephRs` (StatusCode=0 при успехе, 104 при ошибке). `ScenarioId` из XML используется как `tfs_id`.

## 🤝 Контракт решателей

Проверки состояния загрузки (`ctl_chk_status`, `ctl_chk_new`, `ctl_chk_wait`,
`ctl_chk_expire`) таск не останавливают: они возвращают пару `(status, payload)` со
статусом `ok` / `skip` / `fail`, а решение принимает сам таск через `raise_status`.

```python
st, ld_sts = ctl_chk_status(lid, wf['name'], alive='ACTIVE', status='RUNNING', step='RUN')
raise_status(st, ld_sts)
```

`skip` даёт штатный пропуск, поэтому у следующего таска в цепочке нужен
`trigger_rule=NONE_FAILED`. Требования к поведению DAG'ов каталога —
в [`openspec/specs/ctl-worker/spec.md`](../openspec/specs/ctl-worker/spec.md).

## 📊 Статусы загрузок в CTL

### Жизненный цикл потока

```mermaid
stateDiagram-v2
    [*] --> INIT
    INIT --> RUNNING : run_prm()
    RUNNING --> SUCCESS : res ≥ 0
    RUNNING --> ERRORCHECK : res < 0 && retry.left > 0
    RUNNING --> ABORTED : res < 0 && retry.left = 0
    ERRORCHECK --> TIME-WAIT : set delay
    TIME-WAIT --> RUNNING : delay expired
    EVENT-WAIT --> RUNNING : event triggered
    SUCCESS --> COMPLETED : последний этап
    ABORTED --> [*]
    COMPLETED --> [*]
```

---

### Логика обработки результатов

| Код `res` | Сообщение | Иконка | Действие |
|----------|----------|--------|---------|
| `> 0` | `ok` | ✅ | Успех |
| `0` | `no` | ⚠️ | Нет данных (успешно) |
| `-7` | `retry` | ♻️ | Циклический повтор |
| `< 0` (иное) | `error` | ❌ | Ошибка → возможен retry |

---

### Конфигурация retry

```python
retry = {
    'left': N,      # Осталось попыток
    'try': 1,       # Текущая попытка
    'ok': 0,        # Успешные
    'no': 0,        # "Нет данных"
    'err': 0,       # Ошибки
    'on': ['error'],  # При каких статусах делать retry
    'delay': 'hours=+1',  # Начальная задержка
    'add': 'minutes=+5'   # Увеличение задержки при повторах
}
```

**Логика:**
- При `res < 0` и `retry['left'] > 0` → `ERRORCHECK` → `TIME-WAIT`.
- После истечения `delay` → новая попытка (`RUNNING`).
- `delay` увеличивается на `add` при каждом повторе.

---

### Особые случаи

- **Циклический retry (`res = -7`)** — используется при временных сбоях (например, недоступность источника).
- **EVENT-WAIT** — ожидание внешнего события (например, поступления файла).
- **SLA-нарушение** — мониторинг может перевести поток в `ABORTED`.
