# 📡 Тракт Kafka ↔ ТФС
*2026-08-12 19:16 MSK · v1.0 · Чуркин Николай · [nschurkin@sber.ru](mailto:nschurkin@sber.ru)*

Приём обратных квитанций и отправка уведомлений с соблюдением темпа. Общий контур:
сейчас им пользуется ЕР, следующим переезжает xStream.

Конфигурация, утилиты и хранилище тракта живут в `plugins/tfs_utils.py` — не рядом
с дагами. Причина та же, по которой там же лежат `ctl_utils` и `ctl_core`: модулем
пользуются **два** каталога, `tfs_kafka` и `er_export`. Держать настройку у одного
из них значило бы либо связать каталоги, либо развести её по копиям.

Копии тут недопустимы принципиально: если приёмник запишет квитанцию в ClickHouse,
а `wait_confirm` пойдёт искать её в S3, пакет зависнет до таймаута и причина не будет
видна ниоткуда. Поэтому `STORAGE` ровно один.

🔗 Единственная связь с `er_export` — имена двух таблиц, продублированные в обоих
конфигах. Менять синхронно.

---

## Зачем это отдельно

ТФС отвечает на каждое уведомление обратной квитанцией, но кладёт её **в общий топик
по всем маршрутам сразу** (сейчас `TFS.HRPLT.OUT`). Сопоставление — по `RqUID`, результат
передачи — в `Status/StatusCode` (`0` = успех).

Топиков может быть несколько: список в `KAFKA_RCV_TOPICS` (`er_config.py`), одним
коннектом слушаем их все. Из какого топика пришла квитанция, видно в колонке
`kafka_topic`.

Kafka раздаёт сообщение одному потребителю в группе. Значит, читать этот топик из
выгрузок нельзя: кто первым вычитал — тот и забрал, а настоящий адресат ждёт вечно.
Именно так и было до этого дага — ожидание в ER брало **любое** сообщение из топика,
подтверждало им свой пакет, съедало чужую квитанцию и не смотрело на `StatusCode`.

Поэтому потребитель ровно один: `tfs_kafka_rcv`. Он ничего не решает — просто
складывает всё, что пришло, в `export.tfs_receipts`. Ждут своих строк уже сами выгрузки.

```
ТФС → Kafka (KAFKA_RCV_TOPICS) → tfs_kafka_rcv → export.tfs_receipts
                                                       ↑
                          выгрузка ждёт свой RqUID ────┘
```

## Файлы

| Файл | Описание |
| :--- | :--- |
| `tfs_kafka_rcv.py` | DAG `tfs_kafka_rcv` — раз в минуту вычитывает топики и пишет в ClickHouse. Заодно заводит пулы тракта |
| `tfs_kafka_snd.py` | DAG `tfs_kafka_snd` — раз в минуту разгребает очередь `export.er_sent_files`, соблюдая лимиты маршрута |
| `tfs_receipts.sql` | DDL `export.tfs_receipts` для ClickHouse + полезные запросы |
| `tfs_receipts_pg.sql` | То же для PostgreSQL/Greenplum |

Конфигурация — в `plugins/tfs_utils.py`.

Очередь отправки (`export.er_sent_files`) заводится на стороне ЕР — DDL там же,
в `ctl/er_export/er_sent_files.sql`.

## 🗄️ Где хранятся данные

Хранилище сменное, переключатель `STORAGE` в `plugins/tfs_utils.py` — **одно значение
на весь тракт**, включая `er_export`:

| `STORAGE` | Квитанции | Очередь отправки |
| :--- | :--- | :--- |
| `ch` | `export.tfs_receipts` (ClickHouse) | `export.er_sent_files` |
| `pg` | те же таблицы в PostgreSQL/Greenplum, DDL `*_pg.sql` | там же |
| `s3` | объекты рядом с логами | объекты рядом с логами |

Путь для `s3` не задаётся отдельно: берётся из `airflow.cfg` — `remote_base_log_folder`
и `remote_log_conn_id`, поэтому на каждом стенде бакет и коннект верные сами собой.
Раскладка под `{логовый бакет}/tfs/`:

```
receipts/{rq_uid}.json                                 квитанция целиком
queue/pending/{package_ts}__{rq_uid}.json              ждёт отправки
queue/sent/{scenario}/{YYYYMMDDHHMMSS}__{rq_uid}.json  отправлено
```

Плоский `receipts/{rq_uid}.json` — ради `wait_confirm`: он знает только `RqUID`, и поиск
сводится к одному GET. Время отправки лежит **в имени** ключа: по нему считаются окна
лимитов, без чтения объектов. Это заметно дороже, чем `countIf` в СУБД, но при 2000
файлах в сутки терпимо.

У `pg` своя особенность: `ON CONFLICT` не используется, потому что в Greenplum 6 (ядро
PG 9.4) его нет. Дубли допускаются при записи и снимаются при чтении через `DISTINCT ON` —
тот же принцип, что `FINAL` в ClickHouse. По той же причине очередь append-only:
отметка отправки дописывает строку, а не делает `UPDATE`.

## Как работает

Раз в минуту, `max_active_runs=1`. Ран короткий: опрашивает топик, пока идут сообщения,
и выходит по тишине (15 секунд) либо по потолку в 5000 сообщений за ран.

**Порядок операций важен:** сначала вставка в ClickHouse, только потом коммит offset.
При обратном порядке падение между операциями потеряло бы квитанцию навсегда — а её ждёт
выгрузка. Обратная сторона: at-least-once, то есть возможен повтор. Его схлопывает
`ReplacingMergeTree` по `(rq_uid, file_name)`; читать с `FINAL`.

**Битое сообщение не роняет ран** — сохраняется с `status_code = -1` и исходным текстом
в `raw_xml`. Потерять квитанцию хуже, чем сохранить её неразобранной, а застрявшее
сообщение заблокировало бы очередь всем остальным.

**Ненулевой `StatusCode` здесь только логируется.** Это не проблема сборщика: ошибку
покажет та выгрузка, которая ждёт эту квитанцию, — у неё есть контекст пакета.

## Кто ещё трогает этот топик

Никто не должен. Единственный законный конкурент — `tools_test_kafka_rcv` в режиме
`wait` (`ctl/check/test_kafka.py`): он работает в той же consumer group и уводит
сообщения. Запускать его на `TFS.HRPLT.OUT` можно только при остановленном
`tfs_kafka_rcv`. Для разбора инцидентов обычно достаточно `export.tfs_receipts`.

## Диагностика

```sql
-- неуспешные передачи за сутки
SELECT rq_tm, scenario_id, file_name, status_code
FROM export.tfs_receipts FINAL
WHERE status_code != 0 AND received_at >= now() - INTERVAL 1 DAY
ORDER BY received_at DESC;

-- сообщения, которые не разобрались
SELECT received_at, kafka_partition, kafka_offset, substring(raw_xml, 1, 500)
FROM export.tfs_receipts FINAL
WHERE status_code = -1 ORDER BY received_at DESC;
```

Отправлено, но квитанции нет (по данным ЕР) — джойн с реестром отправок:

```sql
SELECT s.file_name, s.notified_at
FROM export.er_sent_files FINAL AS s
LEFT ANTI JOIN export.tfs_receipts FINAL AS r USING (rq_uid)
WHERE s.notified_at > toDateTime64(0, 3)
  AND s.notified_at < now() - INTERVAL 1 HOUR;
```
