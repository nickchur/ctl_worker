# 🚀 ER Export Framework
*2026-08-28 14:06 MSK · v1.14 · Чуркин Николай · [nschurkin@sber.ru](mailto:nschurkin@sber.ru)*

Фреймворк на базе Airflow для автоматизированной выгрузки данных из **ClickHouse** в **S3** с последующей нотификацией системы **TFS** через **Kafka**.

Построен на принципах **Metadata-driven development**: для добавления новой таблицы не требуется написание кода — достаточно добавить запись в управляющую таблицу ClickHouse.

> 👉 **Первый раз здесь?** Начните с [QUICKSTART.md](QUICKSTART.md) — пять шагов и готовые тексты для копирования. Этот файл — справочник: он отвечает на «как устроено», а не на «что нажимать».

## 🏗️ Архитектура

### Основной поток данных

```
ClickHouse → S3 (данные → ZIP) → Kafka (XML-уведомление) → TFS
```

### 📦 Пакет = группа поставок

**Один DAG — один пакет — одна группа — один внешний тикет.** Пакет задаётся парой колонок `replica` + `dag_group`, а даг называется `export_er__<replica>__<dag_group>`:

```
replica = hrplatform_datalab, dag_group = 1     → export_er__hrplatform_datalab__1
replica = hrplatform_datalab, dag_group пуста   → синхронизация подставит 0
dag_group = lm                                  → не обязательно цифра
```

До 28.08.2026 группа была суффиксом внутри `replica` (`hrplatform_datalab__1`) и её приходилось всюду отрезать; теперь это своя колонка.

**Группа есть всегда.** Пустую синхронизация приводит к `0`, потому что имена файлов строятся как `{реплика}__{ts}__{группа}__{table}__{n}_{total}_{rows}.zip`: без группы разделителей `__` на один меньше, и принимающая сторона разбирает имя иначе. Формат имени обязан быть один на все пакеты; в самой `er_wf_meta` строку править не нужно.

Маршрут в TFS (`scenario_id` и префикс в S3) ищется по **реплике**, поэтому в `TFS_MAP` нужна запись только на неё, а новая группа заводится строкой в ClickHouse без правки кода.

В имя архива входит реплика (первой) и группа (за меткой времени), поэтому архивы разных групп не пересекаются именами. А вот **тикет группы не несёт** — его пакеты разводит сама метка времени: её выдаёт таск `make_ts`, сидящий в пуле на одну реплику с единственным слотом, так что группы получают разные секунды (см. «Метка времени пакета»). Внутри одной группы `max_active_runs=1` не даёт двум пакетам родиться одновременно.

## 🌍 Стенды и поведение

**`ENV_STAND`** (при её отсутствии — **`ENVIRONMENT`**) — ограничения строк при выгрузке. Первой читается `ENV_STAND`: её же читают платформенные операторы и соседний `xs_export`:

| Значение | Лимит строк |
| :--- | :--- |
| `PROM` | без ограничений |
| `UAT`, `QA`, `IFT` | 100 строк |
| `DEV` | 100 строк |

Поведение Kafka-уведомлений и ожидания подтверждения управляется параметрами `notify_kafka` и `auto_confirm`, а не стендом.

## ⚡ Pipeline

```
           ┌─ <db>__<tbl>:  init → [build_meta, export_to_s3] → pack_zip  ─┐
make_ts ───┤                                                              │
           └─ <db>__<tbl>:  init → [build_meta, export_to_s3] → pack_zip  ─┤
                                                                          ↓
                        make_summary → wait_confirm → save_status → schedule_next
```

| Таск | Уровень | Описание |
| :--- | :--- | :--- |
| `make_ts` | пакет | 🕐 Берёт метку времени пакета (`now()`), кладёт в XCom `package_ts` и спит секунду под слотом пула. Пул `datalab_export_er_ts__<база>` — один на базовую реплику и ровно на один слот, поэтому группы одной реплики получают разные секунды. |
| `init` | таблица | ⚙️ Delta: читает состояние из `export.extract_current_vw`; при первом запуске — bootstrap от `lower_bound`. Recent: вычисляет окно `[now() - recent_interval, now()]`. Период: применяет `date_from`/`date_to`. |
| `build_meta` | таблица | 🗂️ Генерирует `.meta` JSON и **сверяет** состав колонок с настройкой `fields`. |
| `export_to_s3` | таблица | 📤 Нативная выгрузка ClickHouse → S3 (`HrpClickNativeToS3ListOperator`). Ключ включает имя таблицы. |
| `pack_zip` | таблица | 📦 Потоковая упаковка данных + `.meta` + `.tkt` в ZIP (`stream_zip`). При `send_empty=1` и нулевой дельте — пустой файл. |
| `make_summary` | пакет | 🧾 Пишет **один** тикет `[база]__[ts].tkt` со списком всех архивов пакета и ставит файлы в очередь отправки, выдавая каждому `RqUID`. `trigger_rule=none_failed`: падение любой таблицы блокирует пакет целиком. |
| `wait_confirm` | пакет | ⏳ Ждёт обратные квитанции ТФС в `export.tfs_receipts` по своим `RqUID`. Любой `StatusCode != 0` роняет пакет сразу. Пропускается при `auto_confirm=1`. |
| `save_status` | пакет | 💾 Одна вставка в `export.extract_history` — по строке на таблицу. Разовая выгрузка за период состояние не сохраняет. |
| `schedule_next` | пакет | ⏭️ Автозапуск следующего цикла, если **хотя бы одна** таблица не догнала текущее время. |

## 🚚 Отправка в ТФС: очередь и лимиты

Пакетный DAG сам **ничего не отправляет**. `make_summary` кладёт файлы в
`export.er_sent_files` с `notified_at = 0`, выдавая каждому свой `RqUID`, а шлёт их
`tfs_kafka_snd` — сенсор с часовым окном, опрос раз в 15 секунд, один на весь контур ЕР.

```
пакет: make_summary ──► export.er_sent_files (очередь) ──► tfs_kafka_snd ──► Kafka → ТФС
                                                                                        │
        wait_confirm ◄── export.tfs_receipts ◄── tfs_kafka_rcv ◄── Kafka ◄──────────┘
```

**Почему централизованно.** ТФС декларирует лимиты на маршрут и отбивает лишние файлы:
файлов в секунду, минуту, час и сутки. Считать их можно только там, где видно все
отправки сразу. Прежняя схема — `sleep 1` внутри `produce_msg` плюс 1-слотовый пул
`tfs_<scenario>` — держала темп лишь внутри пакета: пул сериализовал соседние отправки,
но не разводил их по времени, а минутного, часового и суточного бюджетов не было вовсе.

Лимиты живут в `TFS_ROUTES` (`plugins/tfs_utils.py`) рядом с топиком маршрута,
по умолчанию 10/сек, 200/мин, 500/час, 2000/сутки; у `HRPLATFORM-2100` свои — 1/15/100/500.
Счётчики считаются по `export.er_sent_files`, то есть по факту наших отправок.

Все окна **скользящие**, включая суточное: полночь бюджет не обнуляет, он освобождается
постепенно, по мере того как отправки уходят за границу окна.

**⏸️ Паузу отправки** ставят пультом `tfs_kafka_setup` — маршруту, реплике (то есть
одному пакетному дагу) или одному пакету. Постановку в очередь она не трогает: файлы
копятся и уезжают, когда паузу снимут. Подробности — в `ctl/tfs_kafka/README.md`.

**📮 Ручная досылка** — параметры `files` / `scenario` / `replica` у `tfs_kafka_snd`:
имена ставятся в ту же очередь с новыми `RqUID`. Перед постановкой проверяется, что объект
**ещё лежит** в бакете маршрута: файл, который ТФС уже забрал, переотправить нельзя,
и вместо квитанции с кодом 101/108 приходит внятный отказ на нашей стороне. Пакет,
оставшийся в бакете, досылается без ограничений.

### 🔒 Пул `tfs_<ScenarioId>`

Пул на 1 слот **у каждого сценария**, который берёт таск `tfs_kafka_snd` этого сценария.
Пул своего маршрута **обязан брать любой даг, который шлёт в ТФС мимо очереди** — тогда
он не отправит файл ровно в тот момент, когда очередь передаёт пакет. Так уже устроен
`xs_export` (`tfs_out_pool`), и имена совпадают не случайно: пул с другим именем
не пересекался бы с ним и не давал бы ничего.

Чего пул не делает: он **не соблюдает лимиты**. Отправитель мимо очереди не пишет
в `export.er_sent_files`, поэтому его файлы не попадут в счётчики и бюджет маршрута будет
посчитан заниженным. Пул — только взаимное исключение; правильный путь для нового
отправителя — та же очередь.

Пул на сценарий, а не общий: слот удерживается на время опроса (до ~10 секунд) каждые
15 секунд, и на общем пуле два маршрута в него не помещаются — один голодал бы
систематически. Между опросами слот свободен: даг мимо очереди подождёт не дольше одного
опроса, а час ожидания слот не занимает.

Список сценариев (а значит, и тасков с пулами) даг ведёт сам: таск `scan_queue` пишет
найденные в очереди сценарии в Variable `tfs_snd_scenarios`, и на следующем разборе файла
у сценария появляется свой таск — в том числе в уже идущем ране. Обратный ход — тоже через
пул: удалили `tfs_<ScenarioId>` руками, и сценарий уходит из реестра вместе с таском.
Подробности — в `ctl/tfs_kafka/README.md`.

**Пакет уезжает целиком.** Очередь разбирается по `package_ts`: пока не ушли все файлы
одного пакета, к следующему не переходим. Так выполняется требование ЕР «не передаётся
несколько пакетов одновременно» — раньше его держали пулы `tfs_<scenario>`, а теперь
сама очередь.

**Бюджет кончился** — файлы ждут в очереди и уедут, когда окно откроется. Если самая
старая строка ждёт дольше `TFS_QUEUE_ALERT_MIN` (60 минут), `tfs_kafka_snd` краснеет:
затор должен быть виден в мониторинге. Всё, что влезло в бюджет, к этому моменту уже
отправлено.

⚠️ `confirm_timeout` пакета теперь покрывает и ожидание в очереди. При включении
`auto_confirm=0` на боевых выгрузках это значение стоит пересмотреть.

## 📨 Квитанции ТФС

Обратная квитанция приходит по всем маршрутам в один топик `TFS.HRPLT.OUT` и
сопоставляется с отправкой по `RqUID`. Читает топик единственный потребитель — даг
`tfs_kafka_rcv` (см. `ctl/tfs_kafka/`), он складывает всё в хранилище тракта.

Где лежат квитанции и очередь — решает `plugins/tfs_utils.py`. Источник истины один
на весь тракт: **S3 рядом с логами**, туда идёт каждая запись и оттуда каждое чтение.
ClickHouse (`CH_ID`) и PostgreSQL/Greenplum (`PG_CONN`) подключаются зеркалами, если
задан их conn_id, и нужны только чтобы смотреть на тракт запросами; сбой зеркала даёт
предупреждение, но тракт не роняет. `er_export` берёт всё это оттуда же, а не из своего
конфига: разъехавшиеся настройки у писателя и читателя дали бы зависший пакет без
внятной причины.

`wait_confirm` ждёт появления **своих** строк по своим `RqUID`:

- `StatusCode != 0` у любого файла → пакет падает сразу, в ошибке имя файла и код;
- таймаут → падение со списком недостающих, причём отдельно перечислены «ещё не
  отправлены» (очередь стоит) и «отправлены, ответа нет» (молчит ТФС);
- при успехе время квитанции уходит в колонку `confirmed` таблицы `extract_history` —
  раньше туда всегда писался `null`.

### ⏸️ Пакет на паузе отправки

Если файлы пакета придержаны паузой (`Variable tfs_snd_pause`, пульт — даг
`tfs_kafka_setup`), `wait_confirm` уходит в **☮️**: ждать квитанцию по файлу, который
никуда не поедет, значит занять слот пула на час и покраснеть в конце. `save_status`
при этом отрабатывает с `confirmed = null`, дельта двигается, `schedule_next` взводит
следующий цикл — пакет уедет, когда паузу снимут.

Паузу смотрим **дважды и оба раза вне цикла ожидания**: на входе и по истечении таймаута
(тогда это скип, а не падение). Внутри цикла — намеренно нет: пауза, поставленная и снятая
за то же окно, пакета не касается, файлы уедут и квитанции придут, а проверка в цикле
погасила бы такой пакет на ровном месте.

Цена — квитанции по такому пакету никто не ждёт. Их ловит сверка неподтверждённых:
раз в час `tfs_kafka_snd` ищет отправленное без квитанции старше `TFS_STALE_MIN` минут
и пишет предупреждение.

Прежняя реализация читала Kafka напрямую и брала **любое** сообщение из общего топика:
пакет подтверждался чужой квитанцией, настоящий адресат её терял, а `StatusCode`
не проверялся вовсе.

Судьба одного пакета:

```sql
SELECT s.file_name, s.notified_at, r.status_code, r.rq_tm
FROM export.er_sent_files AS s FINAL
LEFT JOIN export.tfs_receipts AS r FINAL USING (rq_uid)
WHERE s.replica = 'hrplatform_datalab__1'   -- в очереди лежит имя пакета: реплика + группа
ORDER BY s.package_ts DESC, s.file_name;
```

## 📊 Режимы выгрузки

**📈 Delta** — инкрементальный, состояние хранится в `export.extract_history`:
- Окно `[time_from, time_to]` читается из `export.extract_current_vw`.
- При первом запуске `time_from = lower_bound` (по умолчанию `1970-01-01`).
- После успешного завершения автоматически запускается следующий цикл.

**🔄 Recent** — скользящее окно без хранения состояния:
- Окно вычисляется как `[now() - recent_interval, now()]`.

**📚 Полная выгрузка** — `full_export = 1` в параметрах поставки:
- Окно дельты **не подставляется вовсе**: в `WHERE` остаётся только то, что задано в `sql_where`, а при пустом `sql_where` запрос уходит без `WHERE` совсем.
- Единственный режим для таблиц, **у которых поля времени нет в принципе**. Без `full_export` пустой `time_field` — ошибка синхронизации: окно строится как `'from' < time_field and time_field <= 'to'`, строить его не из чего.
- Состояние дельты не ведётся: `export.extract_current_vw` не читается, `is_current` всегда `True`, `extract_count` в истории — `null`. Автозапуск не взводится, пакет уходит строго по расписанию группы.
- Ортогонален `is_recent`: при обоих включённых побеждает `full_export`.

**📅 Период** — разовая ручная выгрузка:
- Параметры `date_from` и `date_to` задаются **только вместе**, применяются ко всем таблицам пакета.
- Формат — `ГГГГ-ММ-ДД` или `ГГГГ-ММ-ДД ЧЧ:ММ:СС`, обе границы в одном виде: значения уходят в SQL литералом (`'{from}' < time_field and time_field <= '{to}'`) и между собой сравниваются как строки. Нижняя граница строгая, верхняя включительная — за сутки 1 августа это `2026-08-01` … `2026-08-02`.
- Состояние дельты **не двигается**: `save_status` пропускает запись, `schedule_next` не запускает следующий цикл. Доливка за прошлый месяц не отбрасывает регулярный поток назад.
- Сдвинуть границу «с» у одной таблицы через форму нельзя: `extract_time` у каждой поставки свой, приходит из её состояния и пишется в `extract_history`. Это правка состояния, а не параметр запуска.

## 📦 Формат пакета

Все имена файлов — **строго нижний регистр**, только `[a-z0-9_-]`, длина ≤ 240 байт.

| Файл | Маска |
| :--- | :--- |
| ZIP-архив | `[база]__[YYYYMMDDHHMISS]__[группа]__[table]__[any].zip` |
| Файл данных | `[schema]__[table]__[YYYYMMDDHHMISS]__[any].csv` или `.json` |
| META-описание | то же имя, что у файла данных, расширение `.meta` |
| TKT внутри архива | `[база]__[YYYYMMDDHHMISS].tkt` (одна строка: `filename;rowcount`) |
| TKT снаружи архива | `[база]__[YYYYMMDDHHMISS].tkt` — **один на пакет**, строка на каждый ZIP всех таблиц группы |

Первой в имени стоит **базовая** реплика. Суффикс группы есть только у архива и только **за** меткой времени; тикет его не несёт вовсе. Разделителей `__` в имени архива столько же, сколько было раньше, — позиционный разбор на принимающей стороне не меняется.

### 🕐 Метка времени пакета

Метка времени одна на весь пакет: ЕР требует одинаковый `ts` у архива и тикета, поэтому значение обязано быть неизменным. Считает его таск `make_ts` — первый в ране, один на пакет, — и кладёт в XCom `package_ts`; все остальные таски только читают.

`logical_date` рана на эту роль не годится, хотя и неизменна: суффикс группы из имени тикета убран, а `logical_date` у двух групп одной базовой реплики на общем cron совпадает до секунды — тикеты получили бы одно имя и затёрли друг друга в S3 (`replace=True`). Поэтому `make_ts` берёт `now()` и:

- сидит в пуле `datalab_export_er_ts__<базовая реплика>` — **одном на все группы этой реплики и ровно на один слот**, так что группы проходят его по очереди;
- в конце спит секунду, не отпуская слот: следующая группа возьмёт `now()` не раньше чем через секунду и получит другую метку.

Пул на группу вместо пула на базовую реплику был бы бесполезен: каждая заняла бы собственный слот и стартовали бы они разом.

Пулы заводит `export_er_setup` при синхронизации (`_ensure_pool`), и раньше своего таска пул появиться не может: DAG группы не существует, пока синхронизация не записала её в Variable. Обратная сторона — если метабазу Airflow пересоздали, пул вернёт только прогон настройки с галкой «Синхронизировать принудительно» (обычный уйдёт в скип по контрольной сумме), а до тех пор `make_ts` будет **молча стоять в очереди**, без ошибки. Это первое, что стоит проверить у пакета, который «не запускается».

Метка живёт в XCom, поэтому `clear` одной таблицы или `make_summary` имена файлов не меняет. А `clear` всего рана перезапустит и `make_ts`: пакет поедет с новой меткой, а архивы прошлой попытки останутся в S3 сиротами — раньше, с `logical_date`, они перезаписывались.

Ключ промежуточного файла выгрузки (`{{ ts_nodash }}`) к именам пакета отношения не имеет: файл внутренний и удаляется `pack_zip`.

### 🗂️ Откуда берутся описания в `.meta`

Состав колонок `.meta` считается по `DESCRIBE (<запрос>)` — ровно то, что уедет в заголовок файла данных, с учётом JOIN-ов, алиасов и вычисляемых выражений. А вот **описания** колонок у результата подзапроса взять неоткуда: комментарии есть только у таблиц.

Поэтому источники ищутся в самом запросе — по маске `db.table` в частях `sql_from`, `sql_with`, `sql_join`, **в этом порядке приоритета**. У колонки, которая есть в нескольких таблицах, побеждает описание из `sql_from` — из основной таблицы выгрузки. Это единственный источник базы с тех пор, как колонка `db_name` убрана (28.08.2026): если в `sql_from` написано неквалифицированное имя, кандидатов не найдётся и `.meta` соберётся без описаний — с предупреждением в логе, но без ошибки.

Так же берётся и **комментарий самой таблицы**: он идёт в `description` записи при синхронизации и в `.meta`, если у поставки нет своего `description`.

Почему не по `db_name.extract_name`, как было раньше: `extract_name` — это имя **выгрузки**, а не таблицы. Из одной таблицы делают несколько выгрузок с разными джойнами и условиями, и таблицы с таким именем может не быть вовсе — тогда описания просто терялись (а до правки 2026-08-17 выгрузка ещё и падала на `DESCRIBE TABLE`).

Кандидаты не фильтруются разбором SQL: алиасы вида `t1.person_uuid` под маску тоже попадают, но проверяются одним запросом в `system.columns` и просто не находятся. Ни одной таблицы не нашлось — `.meta` собирается без описаний, а в лог и в отчёт проверки идёт предупреждение.

**Описания можно задать и вручную** — параметром `descriptions` в `params`, словарём `{колонка: текст}` и не обязательно для всех колонок:

```json
{"descriptions": {"person_uuid": "ИД сотрудника", "export_time": "Время выгрузки"}}
```

Приоритет: `params.descriptions` → комментарий колонки источника. Описать можно и служебные колонки (`export_time`, `ctl_action`, `ctl_validfrom`). Имя пишется как в `fields`; hive-суффикс (`level` → `level_`) навешивается сам.

Колонка, которой в выгрузке нет, — **ошибка**: и в проверке `export_er_setup`, и в `build_meta` выгрузки. Описание, написанное для опечатки, иначе молча не доехало бы до КАП, а заметить это можно только глазами в готовом `.meta`.

`descriptions` — единственный параметр, который **сливается по ключам**, а не заменяется целиком: общие колонки описываются раз в строке-дефолте группы, поставка добавляет свои и перебивает одноимённые. Групповой словарь при этом отсеивается по составу каждой поставки — иначе описание общей колонки роняло бы те поставки, где такой колонки нет.

### 🔤 Форматы выгрузки

| `format` | Файл | Заголовок | Особенности |
| :--- | :--- | :--- | :--- |
| `TSVWithNames` | `.csv` | первая строка — имена колонок | разделитель `\t`, `QUOTE_NONE`, экранирование `\` |
| `JSONEachRow` | `.json` | нет | JSON Lines: объект на строку, экранирование через orjson |

Формат задаётся у каждой таблицы отдельно — в одном пакете могут ехать и TSV, и JSON.

Для `JSONEachRow` параметры `pg_array_format`, `xstream_sanitize` и `csv_format_params` не применяются: orjson сериализует массивы и экранирует спецсимволы сам. При нулевой дельте и `send_empty=1` пустой `.json` — файл нулевой длины (заголовка у NDJSON нет).

### META (JSON)

```json
{
  "mask_file":   null,
  "schema_name": "my_schema",
  "table_name":  "my_table",
  "description": "Описание или null",
  "strategy":    "FULL_UK",
  "PK":          ["id"],
  "UK":          ["id"],
  "params":      {"separation": "\t"},
  "columns": [
    {
      "column_name": "id",
      "source_type": "BIGINT",
      "length":      null,
      "notnull":     true,
      "precision":   null,
      "scale":       null,
      "description": null
    }
  ]
}
```

> `UK` — плоский массив: `er_wf_meta.uk` передаётся как есть.
> `params` берётся из `FORMAT_MAP`: `{"separation": "\t"}` для TSV, `{"format": "JSONEachRow"}` для JSON.
> Для `FixedString(N)` → `length=N`; для `Decimal(P,S)` → `precision=P, scale=S, length=P`.

## 🗄️ Управляющая таблица `export.er_wf_meta`

🔑 **Ключ — `(replica, dag_group, schema_name, extract_name)`** (с 28.08.2026; до этого был `(db_name, extract_name)`). Таблица под это пересоздана, DDL и порядок переезда — в `er_wf_meta.sql`.

Что дал новый ключ:

- **признак строки-дефолта ровно один — пустой `extract_name`** (у неё пуст и `schema_name`, поэтому дефолт в группе физически один). Раньше дефолт был обязан нести `db_name = replica`, иначе дефолты всех групп схлопывались по ключу `('', '')`;
- **группа стала отдельной колонкой** `dag_group` вместо суффикса в реплике;
- **одна и та же таблица может входить в разные группы и приезжать в разные схемы** — например, новая версия пакета живёт рядом со старой. Состояние дельты у них разное: в `export.extract_history` имя выгрузки составное, `<dag_id>.<extract_name>` (см. `er_extract_history.sql`);
- ключ записи в форме `export_er_setup` выглядит так же: `hrplatform_datalab/1/learning/lc_items_opened`.

Заодно колонки `schedule` и `is_recent` переехали в `params`, а `db_name` убран совсем — базу источника фреймворк берёт из `sql_from`.

### Два типа строк

| Тип строки | Признак | Смысл |
| :--- | :--- | :--- |
| дефолты группы | `extract_name` **пуст** | значения по умолчанию для всей группы; **обязательна** |
| поставка | `replica` и `extract_name` заполнены | одна таблица |

> ⚠️ Строка-дефолт обязательна. Нет её — группа целиком уходит в ошибку и вместо пакета создаётся заглушка: расписание и групповые параметры брать неоткуда. Заводится она патчем `{"replica": "<группа>", "params": "{\"schedule\": \"30 2 * * *\"}"}`.

Каждое поле разрешается по своему правилу:

| Поле | Как разрешается |
| :--- | :--- |
| `schema_name` | наследуется напрямую: своё непустое перебивает групповое |
| `params` | merge по ключам: умолчания `er_config.py` → группа → таблица |
| `params.schedule` | только из строки-дефолта; в поставке игнорируется с предупреждением |
| `params.is_recent` | наследуется, как любой ключ `params` |
| `description` | своё → комментарий таблицы в ClickHouse → групповое |
| `schema_name` | **не наследуется** — входит в ключ и обязателен у каждой поставки |
| `pk`, `uk`, `fields`, `sql_from`, `sql_join`, `sql_where`, `sql_with`, `sql_settings` | **не наследуются** — всегда про конкретную таблицу |

**`description`** ставит групповой текст последним намеренно: иначе он затёр бы осмысленные комментарии всех таблиц пакета.

**`is_recent` живёт в `params`** (`0` = delta, `1` = recent). Колонкой `UInt8 DEFAULT 0` он не наследовался вовсе: «не задано» было неотличимо от «явно delta», и таблица в recent-группе не смогла бы вернуться к дельте. В JSON ключ либо есть, либо нет — поэтому наследование работает как у остальных параметров, и поставка спокойно переопределяет групповой режим.

**`schedule` живёт в `params` строки-дефолта, обязателен, умолчания у него нет.** Расписание пакета берётся **только** оттуда: колонка позволяла задать его ещё и поставке, и какое из них победит, зависело от того, у кого поле заполнено. Не задано или не разбирается как cron — группа целиком уходит в ошибку, синк краснеет, DAG не создаётся: пакет, поехавший не в своё окно, хуже непоехавшего. Расписание, написанное в `params` поставки, даёт предупреждение, но поставку в пакете оставляет — терять таблицу из-за косметики хуже.

`is_active = 0` на строке-дефолте выключает группу целиком — вместе со всеми её поставками. Для этого синхронизация читает таблицу **без** фильтра по `is_active` и разбирается с ним уже в Python: иначе выключенная строка-дефолт просто исчезла бы из выборки, а поставки поехали бы дальше на умолчаниях из кода — где `notify_kafka = 1`, то есть стендовый пакет молча ушёл бы в ТФС.

### Валидация при синхронизации

Поставка не проходит валидацию (причина — в заметке таска `sync`, полный список в логе и в XCom `errors`), если:

- пустой `sql_from`;
- пустой `schema_name` — он входит в ключ, не наследуется и обязателен у каждой поставки; без него фабрика падает на разборе файла и уносит с собой **все** пакеты, а не только этот;
- **имя вне маски `[A-Za-z0-9_-]` или с `__` внутри** — у `replica`, `dag_group`, `schema_name`, `extract_name`. `__` это разделитель в именах файлов ЕР (`{replica}__{ts}__{dag_group}__{table}__{часть}_{всего}_{строк}.zip`, `{schema}__{table}__{ts}__…`), и лишний сдвигает разбор у принимающей стороны — файл уедет «не тем», молча. Точка разделяет части в ключе выгрузки внутри пакета и в имени состояния дельты (`<dag_id>.<extract_name>`), слэш — части ключа записи, кавычка ломает SQL-литерал, пробел — ключ объекта в S3. Одиночное подчёркивание и дефис разрешены;
- базовая реплика не найдена в `TFS_MAP`;
- `fields` пуст или содержит `*` / `t1.*`;
- неизвестный `format` — проверяется по **слитым** параметрам (дефолты + группа + таблица), чтобы опечатка в строке-дефолте не доехала до фабрики.

Группа целиком уходит в ошибку, если у неё **нет строки-дефолта**, либо у дефолта заполнен `schema_name` (он должен быть пуст), либо в его `params` нет `schedule`, либо расписание не разбирается как cron или пресет Airflow. Последнее проверяется тем же `valid_schedule`, что и у tools-чистильщиков: битое значение иначе доехало бы до `DAG(schedule_interval=…)` и уронило разбор файла вместе со **всеми** пакетами ЕР.

**Любая такая ошибка ломает весь пакет, а не одну поставку.** Тикет в ЕР один на группу, и уехавший неполный состав — это расхождение данных на стороне КАП. Вместо рабочего DAG появляется заглушка (см. ниже), а годные поставки группы в Variable не переносятся.

`schedule` и групповые параметры (`notify_kafka`, `auto_confirm`, `confirm_timeout`, `selfrun_timeout`, `max_active_tasks`), написанные в `params` поставки, — не ошибка, а **предупреждение**: они игнорируются, поставка остаётся, таск синка не краснеет. Иначе красный статус быстро обесценился бы.

### 🚦 Статус таска `sync`

- есть ошибки → таск **падает**. Иначе поломку в метаданных легко не заметить: раньше запись молча выкидывалась, а таск оставался зелёным;
- исправные группы при этом **всё равно записываются** в Variable — опечатка в одной строке не должна замораживать правки по остальным пакетам;
- в заметке: ошибки, предупреждения и сводка «N групп / M выгрузок» — одним блоком, ошибки первыми (`add_note` режет до 1000 символов);
- полные списки — в логе и в XCom: ключи `errors`, `warnings`, `summary`.

### 🚧 DAG-заглушка сломанного пакета

Сломанная группа попадает в Variable без таблиц, но с причинами и расписанием (ключ верхнего уровня — dag_id пакета):

```json
"export_er__hrplatform_datalab__2": {
    "replica": "hrplatform_datalab", "dag_group": "2",
    "schedule": "0 4 * * *", "errors": ["…", "…"], "tables": {}
}
```

Фабрика делает по такой записи DAG с тем же `dag_id` — `export_er__<replica>`, так что рабочий пакет **подменяется**, а не двоится:

- тег `BROKEN` и `❌` в описании — видно прямо в списке DAG-ов;
- полный перечень причин в `doc_md`;
- расписание группы сохраняется, а единственный таск `config_error` при запуске пишет причины в лог и в заметки и **падает**. Пакет продолжает сигналить красным раном в том же ритме, в каком должен был ходить;
- ранее работавший DAG при подмене остаётся включённым и начинает краснеть.

Если фабрика падает на чём-то, что валидация не поймала, цикл регистрации подставляет ту же заглушку с текстом исключения — одна битая группа не уносит остальные ER-пакеты.

## ⚙️ Параметры

Разделены на два уровня. **Групповые** описывают пакет целиком и читаются только из строки-дефолта группы; **табличные** наследуются и переопределяются в каждой поставке.

### 📦 Групповые (`GROUP_PARAMS`)

| Параметр | По умолчанию | Описание |
| :--- | :--- | :--- |
| `schedule` | `''` | **Обязателен.** Cron или пресет Airflow (`@daily`). Только в строке-дефолте: в поставке игнорируется с предупреждением. Пусто или не разбирается — группа уходит в ошибку |
| `notify_kafka` | `1` | `1` = отправлять Kafka-уведомление; `0` = пропустить |
| `auto_confirm` | `1` | `1` = не ждать подтверждения от TFS |
| `confirm_timeout` | `60` мин | Таймаут ожидания квитанций ТФС — включая ожидание в очереди отправки |
| `selfrun_timeout` | `60` мин | Задержка до следующего автозапуска |
| `max_active_tasks` | `4` | Сколько таблиц пакета грузятся одновременно |

### 🗂️ Табличные (`TABLE_PARAMS`)

| Параметр | По умолчанию | Описание |
| :--- | :--- | :--- |
| **⏱️ Дельта** | | |
| `is_recent` | `0` | `0` = дельта (окно из состояния), `1` = recent (скользящее окно). Наследуется от группы, поставка может переопределить |
| `full_export` | `0` | `1` = выгружать таблицу целиком: окно дельты не подставляется, состояние не ведётся |
| `increment` | `60` мин | Шаг дельты; не чаще 1 пакета/час (требование TFS) |
| `overlap` | `0` сек | Перекрытие окна назад (компенсация задержек CDC) |

### 🎛️ DAG Params (ручной запуск)

Состав намеренно скупой: **десять фиксированных параметров плюс по флагу на каждую таблицу пакета**. Все умолчания подобраны так, чтобы автозапуск (`schedule_next` → `trigger_dag(conf={})`) отработал обычный цикл дельты, не заполняя ни одного поля.

| Параметр | Умолчание | Что делает |
| :--- | :--- | :--- |
| `date_from`, `date_to` | пусто | Разовая выгрузка за период: `2026-08-01 00:00:00` либо `2026-08-01`. Задаются только вместе и в одном формате, состояние дельты не двигают |
| `export_path` | пусто | Куда положить файлы пакета: `conn_id://bucket/dir`, например `s3-archive://dataplatform-monitoring-dev/er_dump`. Пусто — штатный путь маршрута ТФС |
| `is_current` | снято | Отметить — состояние считается актуальным, следующий цикл не запускается |
| `notify_kafka` | из группы | Отправлять ли уведомление в Kafka |
| `auto_confirm` | из группы | Не ждать квитанцию ТФС |
| `confirm_timeout` | из группы | Ожидание квитанции; сверху ограничен `execution_timeout` таска |
| `selfrun_timeout` | из группы | Задержка до следующего автозапуска |
| `strategy` | пусто | Стратегия TFS на весь пакет; пусто = из настройки каждой таблицы |
| `max_file_size` | пусто | Предел размера файла на весь пакет; пусто = из настройки каждой таблицы |
| `tbl_<db>__<table>` | `True` | Грузить ли эту поставку в текущем ране |

**Флаги таблиц** — по одному чекбоксу на каждую поставку группы. Снятый флаг скипает всю TaskGroup таблицы: в ZIP и тикет она не попадёт, а её дельта останется на месте — `save_status` и `schedule_next` ходят по XCom и таблицу без него пропускают. Нужно, чтобы перелить одну сломавшуюся поставку, не гоняя весь пакет. Сняли все флаги — ран падает: пустой тикет ТФС от нас не ждёт. Побочный эффект, о котором стоит знать: ран с частью таблиц не взводит автозапуск за пропущенные.

**Путь выгрузки** действует на весь пакет — и на выгрузку данных, и на ZIP, и на тикет: части читаются оттуда же, куда их положил оператор. Поля оператора выставляются при разборе файла, поэтому подмена идёт шаблоном — макрос `s3_target` зовёт тот же `parse_s3_target`, что и питоновские таски, так что цель у всех одна. Каталог необязателен: `s3-archive://bucket` кладёт в корень бакета.

⚠️ Уведомление в ТФС при этом **всё равно уходит**, а состояние дельты **всё равно сдвигается** — так решено сознательно, чтобы параметр ничего не менял за спиной. Но маршрут ТФС ждёт файлы строго по своему префиксу в своём бакете и пакет, уехавший в другое место, не подтвердит; в лог `make_summary` уходит предупреждение. Для разовой выгрузки на сторону снимайте `notify_kafka` и задавайте период.

**Чего в форме нет и почему.** Табличные настройки (`format`, `send_empty`, `pg_array_format`, `xstream_sanitize`, `sanitize_array`, `sanitize_list`, `increment`, `overlap`) живут в `er_wf_meta` и правятся дагом `export_er_setup`. Как параметр пакета они применяли бы одно значение ко **всем** таблицам сразу — то есть чинили одну поставку и молча ломали остальные. По той же причине убраны `extract_time` и `condition`: состояние дельты у каждой таблицы своё и сохраняется в `extract_history`, а пакетный параметр сдвинул бы разом весь пакет.

## 🔀 Стратегии загрузки TFS

| Стратегия | Тип | UK | `ctl_action` из источника | Операция TFS |
| :--- | :--- | :--- | :--- | :--- |
| `APPEND` | INC | нет | любое (игнорируется) | `I` |
| `FULL_UK` | FULL | UK | любое кроме `D` | `I` |
| `FULL_UK` | FULL | UK | `D` | отброс |
| `FULL_NO_UK` | FULL | нет | любое кроме `D` | `I` |
| `FULL_NO_UK` | FULL | нет | `D` | отброс |
| `INC` | INC | UK | любое кроме `D` | `U` (есть запись) / `I` (нет) |
| `INC` | INC | — | `D` | `D` (есть запись) / отброс (нет) |

## ⚙️ Настройка из UI: `export_er_setup`

Даг `export_er_setup` (`er_setup.py`) — единственная точка входа в настройку: смотрит
записи, правит их, проверяет на живом ClickHouse и синхронизирует. Раньше это были два
дага (`export_er_wf_edit` + `export_er_sync`), то есть два рана ради одной правки, а её
результат — сломается ли запрос и что уедет в `.meta` — выяснялся ночью, когда пакет
шёл по расписанию.

| Параметр | Смысл |
| :--- | :--- |
| **Поток** | `— только синхронизация —`, `➕ новая запись` либо ключ существующей записи |
| **Патч** | JSON **только с изменяемыми полями**; для новой записи — вся запись |
| **Записать несмотря на проверку** | Сохранить правку, даже если проверка SQL не прошла |
| **Синхронизировать принудительно** | Не смотреть на контрольную сумму |

Что получится из сочетания первых двух:

| Поток | Патч | Таски |
| :--- | :--- | :--- |
| не выбран | — | `prepare` ☮️ `check` ☮️ `apply` ☮️ **`sync`** |
| выбран | пуст | **`prepare`** **`check`** `apply` ☮️ `sync` ☮️ — просмотр |
| выбран | заполнен | **`prepare`** **`check`** **`apply`** **`sync`** |

Таск `config` (общие настройки) идёт **параллельной веткой** и на эту таблицу не влияет: пустой патч — показ и ☮️, непустой — проверка и запись в `datalab_er_config`. Ветки сходятся на `sync`, у которого `trigger_rule='none_failed'`, поэтому синхронизация работает при любом сочетании скипов.

Поменять расписание группы — `{"params": "{\"schedule\": \"30 2 * * *\"}"}` на её
строке-дефолте (патч заменяет `params` целиком, поэтому перечислять надо все нужные ключи
группы). Выключить запись — `{"is_active": 0}`; у строки-дефолта это гасит весь пакет.
Отдельной кнопки удаления нет.

### 🔍 Проверка

`check` собирает запрос **тем же кодом, что и выгрузка** (`er_config.export_sql`), кладёт
в него заведомо ложное окно дельты и выполняет с внешним `LIMIT 0`. Данных запрос не
читает — ClickHouse обрывает конвейер на `LIMIT 0` до чтения (проверено на бесконечном
`system.numbers`, в том числе с `GROUP BY`), — но разбирает и планирует его целиком.
Обёртка нужна именно для `full_export`: у такой поставки плейсхолдера окна нет вовсе,
и без `LIMIT 0` проверка прочитала бы таблицу целиком.

По колонкам результата собирается `.meta` и сверяется состав с `fields` — той же
`check_fields`, что и в `build_meta` выгрузки. Ловится: несуществующая таблица или
колонка, кривой `sql_join`/`sql_with`/`sql_settings`, разъехавшийся с источником `fields`
и оставшийся квалификатор таблицы в именах колонок (подсказка с готовой строкой замены
приходит прямо в текст ошибки).

Не прошла — **в таблицу ничего не записано**: ошибку видно там, где её сделали. Когда
виновата не запись (источник временно недоступен, таблица ещё не создана), правку
сохраняет галка **Записать несмотря на проверку** — ошибки тогда становятся
предупреждениями, а в заметке остаётся `⚠️ Запись форсирована`.

Структурная проверка (`check_table`: непустой `sql_from`, реплика в `TFS_MAP`,
непустой `schema_name`, явный `fields` без звёздочки, известный `format`) идёт раньше,
в `prepare`, и уже **с наследованием**: пустой `schema_name` у поставки — норма, если он
задан на группе. Там же проверяется, что группа вообще существует: поставку в реплику без
строки-дефолта записать нельзя — синхронизацию она всё равно не пройдёт. У самой
строки-дефолта `check` требует разбираемый `params` и годный `schedule` в нём.

### ⚙️ Общие настройки фреймворка

Константы `er_config.py` — коннекты, бакет, маршруты реплик, лимиты стендов и умолчания параметров — переопределяются из Variable `datalab_er_config`. Код при этом остаётся запасным вариантом: переменной нет, она битая или недоступна — работаем по коду, в лог идёт предупреждение. Ронять разбор файла настройка не имеет права: это все пакеты ЕР разом.

Правится первой группой полей формы `export_er_setup` — **Патч общих настроек**. Патч меняет только перечисленные в нём ключи, `null` возвращает значение из кода:

```json
{"LIMITS": {"DEV": 1000}, "DEFAULT_PARAMS": {"confirm_timeout": 90}}
```

| Ключ | Что задаёт |
| :--- | :--- |
| `CH_ID`, `S3_CONN` | коннекты ClickHouse и S3 |
| `BUCKET` | бакет маршрута ТФС |
| `TFS_MAP` | `replica → ["ScenarioId", "префикс в S3"]`; новая базовая реплика заводится без выкладки |
| `LIMITS` | лимит строк по стендам; `0` = без ограничений |
| `DEFAULT_PARAMS` | умолчания групповых и табличных параметров, **слияние по ключам** |

Остальное намеренно живёт только в коде: `DEF_ARGS` содержит функции; `FORMAT_MAP`, `TYPE_MAP`, служебные колонки и список Hive-слов — это контракт обмена с КАП, а не настройка стенда; `TS_POOL_SLOTS` обязан быть `1` по устройству пула меток времени; `POOL_SLOTS` не берём, потому что `ensure_pool` существующий пул не трогает — правка выглядела бы применённой, не будучи ею.

Таск `config` проверяет патч строго — неизвестный ключ, чужой тип, `TFS_MAP` не парой, нецелой `LIMITS`: ран красный, переменная не тронута. На разборе файла те же случаи только предупреждают.

⏳ **Применяется со следующего разбора файла** (~30 секунд): константы читаются на парсинге. Синк в этом же ране работает ещё со старым снимком конфига и обычно уходит в скип по сумме — но снимок входит в контрольную сумму, поэтому, как только планировщик перечитает файл, сумма разойдётся сама и следующий синк пересоберёт пакеты. Форсировать ничего не нужно.

### 🔐 Контрольная сумма синхронизации

`sync` идёт в каждом ране, но при неизменной настройке уходит в скип ☮️. Сумма — `sha256`
по строкам таблицы **и по снимку конфига** (`DEFAULT_PARAMS`, `GROUP_PARAMS`, `FORMAT_MAP`,
`INHERITED`, `TFS_MAP`); вторая половина обязательна, иначе правка умолчаний в коде,
не трогающая ни одной строки таблицы, молча не доехала бы до Variable. Хранится
в `datalab_er_wf_hash` и записывается **только при чистом прогоне**: иначе сломанный
пакет отрапортовал бы о себе однажды и замолчал. Скип не срабатывает, если `datalab_er_wfs`
пуста или отсутствует, — удалённую руками переменную иначе не восстановил бы никто.
Принудительно — галкой или удалением `datalab_er_wf_hash`.

### 📋 Мелочи, которые обычно спрашивают

**Почему два поля, а не одно.** Параметр с `examples` Airflow рендерит выпадающим списком
**вместо** свободного поля, а подставить выбранное значение в соседнее поле статическая
форма не умеет. Поэтому выбор и правка разведены: список говорит, *какую* запись берём,
патч — *что* в ней меняем. Копировать весь JSON записи при этом не нужно.

**Список записей** строится при разборе файла из Variable `datalab_er_wf_meta`, которую
наполняет `sync` этого же дага (сырые строки таблицы, включая выключенные). В ClickHouse
на каждом парсинге не ходим — это лишняя нагрузка и Broken DAG при недоступности базы.
Следствие: только что созданная запись появится в списке через десяток секунд, когда
планировщик перечитает файл.

**Где результаты.** Полностью — в логе и в XCom: `before` (состояние до), `check` (запрос,
колонки, `.meta`, ошибки и предупреждения), `after` (состояние после), у синхронизации —
`errors`, `warnings`, `summary`. В заметках только короткие итоги: `add_note` режет
их до 1000 символов.

**Почему сборка запроса живёт в `er_config.py`.** Проверка обязана собирать запрос тем же
кодом, что и выгрузка, иначе она проверяет не то, что поедет, а две сборки разъезжаются
на первой же правке. Импортировать `er_export.py` ради этого нельзя — это файл с DAG-ами.

Обратное тоже верно, и поэтому даг лежит отдельным файлом, а не в `er_config.py`:
`_process_modules` добавляет к найденным дагам `DagContext.autoregistered_dags`, куда
попадает всё созданное декоратором `@dag` за время разбора текущего файла. Конфиг
импортируют оба DAG-файла — даг из него привязался бы к каждому. **Модуль, который
импортируют DAG-файлы, сам DAG-и создавать не должен.**

Освободить имя `er_config.py`, переименовав конфиг в `er_common.py`, нельзя: в проде
всё разворачивается в пакет `CI06932748.analytics.datalab.export_er/`, где `er_common.py`
занят легаси-модулем старого ER.

Правка существующей записи — это **вставка новой версии**: `ReplacingMergeTree` схлопнет
её по `(replica, dag_group, schema_name, extract_name)` при фоновом MERGE. В заметке к прогону остаётся диф
«поле: было → стало».

## ➕ Как завести новый пакет

### 1. Строка-дефолт группы

```sql
INSERT INTO export.er_wf_meta (replica, dag_group, description, params)
VALUES (
    'hrplatform_datalab',
    '1',
    'Пакет 1: справочники обучения',
    -- расписание живёт здесь и только здесь
    '{"schedule": "55 0 * * *", "auto_confirm": 0, "max_active_tasks": 2}'
);
```

У строки-дефолта пусты `extract_name` **и** `schema_name` — это её признак и то,
что делает её единственной в группе.

### 2. Поставки группы

```sql
INSERT INTO export.er_wf_meta
    (replica, dag_group, schema_name, extract_name, uk, fields, sql_from, sql_where, params)
VALUES (
    'hrplatform_datalab',
    '1',
    'target_schema',
    'my_table',
    ['id'],
    ['id', 'name', 'updated_at'],   -- явный список обязателен
    'my_database.my_table',
    '',
    '{"strategy": "FULL_UK"}'
);
```

### Поставка с JOIN

При непустом `sql_join` состав `fields` особенно важен: без него `*` развернулось бы в колонки обеих таблиц, и дубли справа (`t2.col`) уехали бы в CSV и в `.meta`.

```sql
INSERT INTO export.er_wf_meta
    (replica, dag_group, schema_name, extract_name, uk, fields, sql_from, sql_join, sql_where, params)
VALUES (
    'hrplatform_datalab',
    '1',
    'target_schema',
    'my_table',
    ['id'],
    ['t1.id', 't1.name', 't2.flag'],
    'my_database.my_table t1',
    'LEFT JOIN my_database_export.my_table_exp t2 ON t1.id = t2.id',
    '',
    '{"strategy": "FULL_UK"}'
);
```

### Тяжёлый запрос с CTE и SETTINGS CH

```sql
INSERT INTO export.er_wf_meta
    (replica, dag_group, schema_name, extract_name, uk, fields,
     sql_with, sql_from, sql_where, sql_settings, params)
VALUES (
    'hrplatform_datalab',
    '1',
    'target_schema',
    'my_heavy_table',
    ['id'],
    ['id', 'updated_at'],
    'WITH cte AS (SELECT id, max(updated_at) AS updated_at FROM my_database.my_heavy_table GROUP BY id)',
    'cte',
    '',
    'max_threads=2, max_memory_usage=10000000000',
    '{"strategy": "FULL_UK"}'
);
```

### 🧮 Агрегация: GROUP BY, HAVING, ORDER BY

Отдельного поля под `GROUP BY` в `er_wf_meta` нет, и оно не нужно — всё это пишется хвостом в `sql_where`. Работает за счёт **явного `{condition}`**: увидев плейсхолдер, фабрика подставляет окно на его место и отдаёт условие как есть. Без плейсхолдера окно дописывается спереди по шаблону `{condition} AND (<ваше условие>)`, и `GROUP BY` попадает внутрь скобок — запрос не разберётся.

```sql
INSERT INTO export.er_wf_meta
    (replica, dag_group, schema_name, extract_name, uk, fields, sql_from, sql_where, params)
VALUES (
    'hrplatform_datalab',
    '1',
    'target_schema',
    'lc_sessions',
    ['person_uuid'],
    ['person_uuid',
     'count() AS sessions_cnt',
     'sum(s.seconds) AS total_seconds',
     'max(insert_time) AS insert_time'],
    'my_database.lc_sessions AS s',
    '{condition} AND s.seconds > 0 GROUP BY person_uuid HAVING sum(s.seconds) > 60',
    '{"time_field": "s.insert_time"}'
);
```

- служебные колонки (`'I' as ctl_action`, `now64(6) as ctl_validfrom`) с `GROUP BY` уживаются: ClickHouse считает их константами и в группировку не требует;
- `HAVING` и `ORDER BY` пишутся туда же, после `GROUP BY`; `SETTINGS` фабрика ставит последним сама;
- при `full_export = 1` плейсхолдер не нужен вовсе — окно и так не подставляется, `sql_where` уходит в запрос нетронутым.

### 🏷️ `time_field` квалифицируем всегда

`time_field` подставляется в окно как есть (`'from' < time_field and time_field <= 'to'`), поэтому короткое имя ловит сразу две проблемы ClickHouse. **Правило простое: у поля времени всегда пишем префикс таблицы** — `s.insert_time`, `i.insert_time`. Годится и полное имя таблицы (`lc_sessions.insert_time`), алиас просто короче.

- **JOIN.** Если такая же колонка есть в присоединяемой таблице, короткое имя неоднозначно.
- **Агрегация.** Алиас в `SELECT` затеняет одноимённую колонку: у поставки с `max(insert_time) AS insert_time` голая ссылка в `WHERE` резолвится в алиас, то есть в агрегат, и запрос падает с `ILLEGAL_AGGREGATION`. Квалифицированная ссылка всегда указывает на колонку — переименовывать алиас не нужно.

### ⚠️ В JOIN на три и более таблицы алиасьте каждое поле

При **двух и более** `JOIN` ClickHouse оставляет префикс таблицы в имени результата у колонки, чьё короткое имя есть ещё в одной из соединяемых таблиц: `i.status` станет `status`, а `i.person_uuid` так и останется `i.person_uuid`. С одним `JOIN` префикс срезается всегда — то есть поведение меняется от добавления третьей таблицы. Точка уедет и в заголовок файла данных, и в `.meta`, поэтому в `fields` пишем `'i.person_uuid AS person_uuid'`, а не `'i.person_uuid'`.

Ловит это сверка состава в `build_meta`: пакет падает, а в сообщении — готовые строки замены.

### 🕐 Окно дельты внутри CTE

Плейсхолдер `{condition}` можно поставить прямо в `sql_with`, `sql_from` или `sql_join` — тогда фильтр отработает **до** агрегации, что на больших таблицах на порядок дешевле внешнего `WHERE`. Найдя плейсхолдер в любой из этих частей, фабрика наружу окно не дописывает, и в `sql_where` остаётся только бизнес-условие.

```sql
sql_with:  'WITH agg AS (SELECT person_uuid, max(pct) AS mx FROM db.progress
            WHERE {condition} GROUP BY person_uuid)'
sql_from:  'agg AS a'
sql_where: 'a.mx > 0'
```

## 🛠️ Технические детали

- 🔍 **Сверка состава колонок** (`er_config.check_fields`, общая у выгрузки и у проверки в `export_er_setup`): сравнивается результат `DESCRIBE` итогового запроса с именами из `fields` и падает при расхождении. Смысл — новая колонка в источнике не доезжает до КАП сама, только через правку настройки. Имя выводится из выражения, если у него есть явный алиас (`expr as name`) или это простая колонка (`t1.col`); для выражений без алиаса (`cast(x as String)`) имя предсказать нельзя, такая позиция сверяется только по количеству, а в лог идёт предупреждение с предложением добавить алиас. Если в имени колонки запроса осталась точка, сверка отдельно объясняет про квалификатор в JOIN и печатает готовые строки замены для `fields`.
- 🔤 **Hive reserved words**: `build_meta` добавляет суффикс `_` к именам колонок, совпадающим с зарезервированными словами Hive (все версии 1.2–4.0).
- 🕳️ **`join_use_nulls` виден только в JSON**: настройка доходит и до запроса выгрузки, и до `DESCRIBE` (в `.meta` колонка получает `notnull: false`), но в файле `NULL` сохраняется лишь у `JSONEachRow` — там это честный `null`. В `TSVWithNames` `csv.writer` оператора пишет `None` пустым полем, `\N` не появляется, и `NULL` становится неотличим от пустой строки. Массивы теряют различие в обоих форматах: `Array` под `join_use_nulls` не становится `Nullable`, пропуск в `LEFT JOIN` даёт `[]`.
- 📭 **send_empty**: задаётся только в `er_wf_meta`, параметра запуска у него нет. При `send_empty=1` и нулевой дельте `pack_zip` создаёт ZIP с пустым файлом данных + TKT + META. Соответствует требованию TFS: «пустой пакет выгружается по расписанию даже при отсутствии изменений».
- 🔄 **Синхронизация**: `export_er_setup` расписания не имеет — только ручной Trigger DAG. Синхронизация идёт в каждом ране и скипается ☮️, когда контрольная сумма настройки не изменилась.
- 🏊 **Pools**: `datalab_export_er` (20 слотов) создаёт `export_er_setup`; пулы отправки `tfs_<ScenarioId>` (по 1 слоту) — уже забота `tfs_kafka`: известные заводит `tfs_kafka_rcv`, новые — таск `scan_queue`. Требование «не передаётся несколько пакетов одновременно» выполняет сама очередь `tfs_kafka_snd`, а пул нужен против отправителей мимо неё (`xs_export` берёт эти же имена).
- 💧 **Стриминг**: ZIP-архивация потребляет минимум памяти — `stream_zip` + multipart-загрузка в S3 без буферизации всего файла.
- 🔒 **Изоляция**: фреймворк не зависит от общих `plugins`, используя собственные хелперы в `er_config.py`.
- ✅ **Идемпотентность**: Variable переписывается, только если данные изменились, а сам таск синхронизации скипается по контрольной сумме.
- 📝 **on_callback**: при падении таска добавляет заметку с трейсом в Airflow UI на уровне Task и DAG Run; при успехе — на уровне Task.

## 🚀 Запуск нового пакета

1. Завести строки в `export.er_wf_meta`: сначала строку-дефолт группы (`extract_name = ''`, в `params` — `schedule`), затем по строке на поставку с явным `fields`. Без строки-дефолта группа не собирается.
2. Прогнать `export_er_setup` (можно без выбора потока — тогда это чистая синхронизация), сверить Variable `datalab_er_wfs`. При ошибках таск `sync` краснеет, причины — в заметке, полные списки в логе и в XCom.
3. Снять с паузы DAG `export_er__<replica>` — фабрика создаёт его на паузе.
