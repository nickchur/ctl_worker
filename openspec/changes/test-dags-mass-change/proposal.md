# Контроль сериализации переживает массовое изменение DAG'ов

## Why

12.09.2026 на альфе `tools_test_dags` упал на `compare.find_changed`: после обновления core
сериализация поменялась у 685 DAG'ов, а таск возвращал их списком через `return`.
XCom-бэкенд контура (`LimitedXComBackend` в core) не принимает список длиннее 500
элементов. `snapshot_dags` за ним не запустился и новые версии не записал, а изменившиеся
считаются от последней записанной версии — поэтому падение повторялось бы каждую ночь, пока
кто-то не вмешается. Следом упал бы и сам `snapshot_dags`: пары для сравнения он тоже
отдаёт списком, тех же 685.

Это нарушает требование «Проверка сериализации никогда не роняет прогон»: сценарий
«изменилось после выкладки» ждёт зелёного прогона.

## What Changes

- Между задачами ветки `compare` списки через `return` больше не ходят: `find_changed`
  возвращает счётчики, `snapshot_dags` отбирает изменившиеся сам по тем же хэшам.
- Версии пишутся всем изменившимся, сколько бы их ни было.
- На сравнение за прогон уходит не больше `COMPARE_LIMIT` (100) пар, свежие первыми;
  остальные — числом в сводке и списком в XCom `not_compared`.

## Capabilities

### New Capabilities

Нет.

### Modified Capabilities

- `check`: требование «Проверка сериализации никогда не роняет прогон» — сценарий
  массового изменения.

## Impact

- `check/test_dags.py` — `find_changed`, `snapshot_dags`, `summary`, связка задач.
- `check/readme.md` — строка про массовое изменение.
- Внешние системы: S3 (`dag_snapshots/`) — пишется столько же, сколько раньше при удачном
  прогоне; метабаза — те же SELECT'ы.
