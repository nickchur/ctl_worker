# 🚀 ER Export Framework
*2026-08-12 19:16 MSK · v1.0 · Чуркин Николай · [nschurkin@sber.ru](mailto:nschurkin@sber.ru)*

Фреймворк на базе Airflow для автоматизированной выгрузки данных из **ClickHouse** в **S3** с последующей нотификацией системы **TFS** через **Kafka**.

Построен на принципах **Metadata-driven development**: для добавления новой таблицы не требуется написание кода — достаточно добавить запись в управляющую таблицу ClickHouse.

---

## 🏗️ Архитектура

### Основной поток данных

```
ClickHouse → S3 (данные → ZIP) → Kafka (XML-уведомление) → TFS
```

### 📦 Пакет = группа поставок

**Один DAG — один пакет — одна группа — один внешний тикет.** Группа задаётся значением `replica` целиком: суффикс после `__` отделяет группы одной реплики друг от друга.

```
hrplatform_datalab        — реплика без группировки
hrplatform_datalab__1     — группа 1
hrplatform_datalab__lm    — суффикс произвольный, не обязательно цифровой
```

Маршрут в TFS (`scenario_id` и префикс в S3) ищется по **базовой** реплике — части до первого `__`, поэтому в `TFS_MAP` нужна запись только на базу, а новая группа заводится строкой в ClickHouse без правки кода.

Полная `replica` входит и в имя архива, и в имя тикета, поэтому имена пакетов разных групп не пересекаются даже при совпадении секунды запуска. Внутри одной группы `max_active_runs=1` не даёт двум пакетам родиться одновременно.

## 🌍 Стенды и поведение

**`ENV_STAND`** (при её отсутствии — **`ENVIRONMENT`**) — ограничения строк при выгрузке. Первой читается `ENV_STAND`: её же читают платформенные операторы и соседний `xs_export`:

| Значение | Лимит строк |
| :--- | :--- |
| `PROM` | без ограничений |
| `UAT`, `QA`, `IFT` | 100 строк |
| `DEV` | 100 строк; `export_er_sync` создаёт `export.er_wf_meta` автоматически если таблица отсутствует |

Оттуда же берётся **`MAX_FILE_SIZE`** — предел размера одного файла данных: `10GB` на `PROM`, `1GB` на остальных. Это свойство стенда, а не таблицы: делить поток крупнее имеет смысл там, где канал до ТФС это выдерживает. Значение подставляется умолчанием в параметр запуска «Max file size», в `er_wf_meta` его нет.

Поведение Kafka-уведомлений и ожидания подтверждения управляется параметрами `notify_kafka` и `auto_confirm`, а не стендом.

## ⚡ Pipeline

```
<db>__<tbl>:  init → [build_meta, export_to_s3] → pack_zip  ─┐
<db>__<tbl>:  init → [build_meta, export_to_s3] → pack_zip  ─┤
                                                             ↓
              make_summary → wait_confirm → save_status → schedule_next
```

| Таск | Уровень | Описание |
| :--- | :--- | :--- |
| `init` | таблица | ⚙️ Delta: читает состояние из `export.extract_current_vw`; при первом запуске — bootstrap от `lower_bound`. Recent: вычисляет окно `[now() - recent_interval, now()]`. Период: применяет `date_from`/`date_to`. |
| `build_meta` | таблица | 🗂️ Генерирует `.meta` JSON и **сверяет** состав колонок с настройкой `fields`. |
| `export_to_s3` | таблица | 📤 Нативная выгрузка ClickHouse → S3 (`HrpClickNativeToS3ListOperator`). Ключ включает имя таблицы. |
| `pack_zip` | таблица | 📦 Потоковая упаковка данных + `.meta` + `.tkt` в ZIP (`stream_zip`). При `send_empty=1` и нулевой дельте — пустой файл. |
| `make_summary` | пакет | 🧾 Пишет **один** тикет `[replica]__[ts].tkt` со списком всех архивов пакета и ставит файлы в очередь отправки, выдавая каждому `RqUID`. `trigger_rule=none_failed`: падение любой таблицы блокирует пакет целиком. |
| `wait_confirm` | пакет | ⏳ Ждёт обратные квитанции ТФС в `export.tfs_receipts` по своим `RqUID`. Любой `StatusCode != 0` роняет пакет сразу. Пропускается при `auto_confirm=1`. |
| `save_status` | пакет | 💾 Одна вставка в `export.extract_history` — по строке на таблицу. Разовая выгрузка за период состояние не сохраняет. |
| `schedule_next` | пакет | ⏭️ Автозапуск следующего цикла, если **хотя бы одна** таблица не догнала текущее время. |

## 🚚 Отправка в ТФС: очередь и лимиты

Пакетный DAG сам **ничего не отправляет**. `make_summary` кладёт файлы в
`export.er_sent_files` с `notified_at = 0`, выдавая каждому свой `RqUID`, а шлёт их
`tfs_kafka_snd` — раз в минуту, один на весь контур ЕР.

```
пакет: make_summary ──► export.er_sent_files (очередь) ──► tfs_kafka_snd ──► Kafka → ТФС
                                                                                        │
        wait_confirm ◄── export.tfs_receipts ◄── tfs_kafka_rcv ◄── Kafka ◄──────────┘
```

**Почему централизованно.** ТФС декларирует лимиты на маршрут и отбивает лишние файлы:
файлов в секунду, минуту, час и сутки. Считать их можно только там, где видно все
отправки сразу. Прежняя схема — `sleep 1` внутри `produce_msg` плюс 1-слотовый пул
`tfs_<scenario>` — держала темп лишь внутри пакета: пул сериализовал соседние отправки,
но не разводил их по времени, а минутного, часового и суточного бюджетов не было вовсе.

Лимиты живут в `TFS_LIMITS` (`er_config.py`), по умолчанию 10/сек, 200/мин, 500/час,
2000/сутки; у `HRPLATFORM-2100` свои — 1/15/100/500. Счётчики считаются по
`export.er_sent_files`, то есть по факту наших отправок.

Все окна **скользящие**, включая суточное: полночь бюджет не обнуляет, он освобождается
постепенно, по мере того как отправки уходят за границу окна.

### 🔒 Пул `tfs_send`

Пул на 1 слот, который берёт `tfs_kafka_snd`. Его **обязан брать любой даг, который
шлёт в ТФС мимо очереди** — тогда он не отправит файл ровно в тот момент, когда очередь
передаёт пакет.

Чего пул не делает: он **не соблюдает лимиты**. Отправитель мимо очереди не пишет
в `export.er_sent_files`, поэтому его файлы не попадут в счётчики и бюджет маршрута будет
посчитан заниженным. Пул — только взаимное исключение; правильный путь для нового
отправителя — та же очередь.

Пул один общий, а не `tfs_<scenario>`: пул назначается таску при разборе файла,
а `tfs_kafka_snd` — один таск на все сценарии и заранее не знает, чьи файлы попадутся
в очереди. Слот удерживается весь ран (до ~50 секунд), значит даг мимо очереди подождёт
не дольше этого.

**Пакет уезжает целиком.** Очередь разбирается по `package_ts`: пока не ушли все файлы
одного пакета, к следующему не переходим. Так выполняется требование ЕР «не передаётся
несколько пакетов одновременно» — раньше его держали пулы `tfs_<scenario>`, а теперь
сама очередь.

**Бюджет кончился** — файлы ждут в очереди и уедут, когда окно откроется. Если самая
старая строка ждёт дольше `TFS_QUEUE_ALERT_MIN` (60 минут), `tfs_kafka_snd` краснеет:
затор должен быть виден в мониторинге. Всё, что влезло в бюджет, к этому моменту уже
отправлено.

⚠️ `confirm_timeout` пакета теперь покрывает и ожидание в очереди. При включении
`auto_confirm=0` на боевых выгрузках это значение стоит пересмотреть.

## 📨 Квитанции ТФС

Обратная квитанция приходит по всем маршрутам в один топик `TFS.HRPLT.OUT` и
сопоставляется с отправкой по `RqUID`. Читает топик единственный потребитель — даг
`tfs_kafka_rcv` (см. `ctl/tfs_kafka/`), он складывает всё в хранилище тракта.

Где именно лежат квитанции и очередь — решает `STORAGE` в `plugins/tfs_utils.py`:
ClickHouse, PostgreSQL/Greenplum или S3 рядом с логами. Значение одно на весь тракт,
и `er_export` берёт его оттуда же, а не из своего конфига: разъехавшиеся настройки
у писателя и читателя дали бы зависший пакет без внятной причины.

`wait_confirm` ждёт появления **своих** строк по своим `RqUID`:

- `StatusCode != 0` у любого файла → пакет падает сразу, в ошибке имя файла и код;
- таймаут → падение со списком недостающих, причём отдельно перечислены «ещё не
  отправлены» (очередь стоит) и «отправлены, ответа нет» (молчит ТФС);
- при успехе время квитанции уходит в колонку `confirmed` таблицы `extract_history` —
  раньше туда всегда писался `null`.

Прежняя реализация читала Kafka напрямую и брала **любое** сообщение из общего топика:
пакет подтверждался чужой квитанцией, настоящий адресат её терял, а `StatusCode`
не проверялся вовсе.

Судьба одного пакета:

```sql
SELECT s.file_name, s.notified_at, r.status_code, r.rq_tm
FROM export.er_sent_files FINAL AS s
LEFT JOIN export.tfs_receipts FINAL AS r USING (rq_uid)
WHERE s.replica = 'hrplatform_datalab__1'
ORDER BY s.package_ts DESC, s.file_name;
```

## 📊 Режимы выгрузки

**📈 Delta** — инкрементальный, состояние хранится в `export.extract_history`:
- Окно `[time_from, time_to]` читается из `export.extract_current_vw`.
- При первом запуске `time_from = lower_bound` (по умолчанию `1970-01-01`).
- После успешного завершения автоматически запускается следующий цикл.

**🔄 Recent** — скользящее окно без хранения состояния:
- Окно вычисляется как `[now() - recent_interval, now()]`.

**📚 Полная выгрузка** — `full_export = 1` в параметрах поставки:
- Окно дельты **не подставляется вовсе**: в `WHERE` остаётся только то, что задано в `sql_where`, а при пустом `sql_where` запрос уходит без `WHERE` совсем.
- Единственный режим для таблиц, **у которых поля времени нет в принципе**. Без `full_export` пустой `time_field` — ошибка синхронизации: окно строится как `'from' < time_field and time_field <= 'to'`, строить его не из чего.
- Состояние дельты не ведётся: `export.extract_current_vw` не читается, `is_current` всегда `True`, `extract_count` в истории — `null`. Автозапуск не взводится, пакет уходит строго по расписанию группы.
- Ортогонален `is_recent`: при обоих включённых побеждает `full_export`.

**📅 Период** — разовая ручная выгрузка:
- Параметры `date_from` и `date_to` задаются **только вместе**, применяются ко всем таблицам пакета.
- Формат — `ГГГГ-ММ-ДД` или `ГГГГ-ММ-ДД ЧЧ:ММ:СС`, обе границы в одном виде: значения уходят в SQL литералом (`'{from}' < time_field and time_field <= '{to}'`) и между собой сравниваются как строки. Нижняя граница строгая, верхняя включительная — за сутки 1 августа это `2026-08-01` … `2026-08-02`.
- Состояние дельты **не двигается**: `save_status` пропускает запись, `schedule_next` не запускает следующий цикл. Доливка за прошлый месяц не отбрасывает регулярный поток назад.
- Сдвинуть границу «с» у одной таблицы через форму нельзя: `extract_time` у каждой поставки свой, приходит из её состояния и пишется в `extract_history`. Это правка состояния, а не параметр запуска.

## 📦 Формат пакета

Все имена файлов — **строго нижний регистр**, только `[a-z0-9_-]`, длина ≤ 240 байт.

| Файл | Маска |
| :--- | :--- |
| ZIP-архив | `[replica]__[YYYYMMDDHHMISS]__[table]__[any].zip` |
| Файл данных | `[schema]__[table]__[YYYYMMDDHHMISS]__[any].csv` или `.json` |
| META-описание | то же имя, что у файла данных, расширение `.meta` |
| TKT внутри архива | `[replica]__[YYYYMMDDHHMISS].tkt` (одна строка: `filename;rowcount`) |
| TKT снаружи архива | `[replica]__[YYYYMMDDHHMISS].tkt` — **один на пакет**, строка на каждый ZIP всех таблиц группы |

Метка времени одна на весь пакет — `logical_date` рана. ЕР требует одинаковый `ts` у архива и тикета, поэтому значение обязано быть неизменным: `dag_run.start_date` не годится, он перештамповывается при каждом переходе рана в RUNNING, и после `clear` упавшей таблицы её архивы получили бы новое время, а тикет — третье. `logical_date` у рана одна навсегда и совпадает с `{{ ts_nodash }}` в ключе промежуточного файла.

### 🔤 Форматы выгрузки

| `format` | Файл | Заголовок | Особенности |
| :--- | :--- | :--- | :--- |
| `TSVWithNames` | `.csv` | первая строка — имена колонок | разделитель `\t`, `QUOTE_NONE`, экранирование `\` |
| `JSONEachRow` | `.json` | нет | JSON Lines: объект на строку, экранирование через orjson |

Формат задаётся у каждой таблицы отдельно — в одном пакете могут ехать и TSV, и JSON.

Для `JSONEachRow` параметры `pg_array_format`, `xstream_sanitize` и `csv_format_params` не применяются: orjson сериализует массивы и экранирует спецсимволы сам. При нулевой дельте и `send_empty=1` пустой `.json` — файл нулевой длины (заголовка у NDJSON нет).

### META (JSON)

```json
{
  "mask_file":   null,
  "schema_name": "my_schema",
  "table_name":  "my_table",
  "description": "Описание или null",
  "strategy":    "FULL_UK",
  "PK":          ["id"],
  "UK":          ["id"],
  "params":      {"separation": "\t"},
  "columns": [
    {
      "column_name": "id",
      "source_type": "BIGINT",
      "length":      null,
      "notnull":     true,
      "precision":   null,
      "scale":       null,
      "description": null
    }
  ]
}
```

> `UK` — плоский массив: `er_wf_meta.uk` передаётся как есть.
> `params` берётся из `FORMAT_MAP`: `{"separation": "\t"}` для TSV, `{"format": "JSONEachRow"}` для JSON.
> Для `FixedString(N)` → `length=N`; для `Decimal(P,S)` → `precision=P, scale=S, length=P`.

## 🗄️ Управляющая таблица `export.er_wf_meta`

Структура таблицы не менялась: те же колонки, тот же ключ `(db_name, extract_name)`. Пересоздавать её не нужно.

Строка `ENGINE` в `er_wf_meta.sql` при этом отличается от того, что лежало в репозитории раньше: там был устаревший путь `'/clickhouse/tables/{shard}/export/er_wf_meta'`, а боевая таблица создана по `'/clickhouse/tables/er_wf_meta_{uuid}'`. Файл приведён к боевому значению — менялась не таблица, а её описание.

### Два типа строк

| Тип строки | Признак | Смысл |
| :--- | :--- | :--- |
| дефолты группы | `extract_name` **пуст**, `db_name` = `replica` | значения по умолчанию для всей группы |
| поставка | `replica` и `extract_name` заполнены | одна таблица |

> ⚠️ У строки-дефолта `db_name` обязан быть равен `replica`. Ключ таблицы — `(db_name, extract_name)`, `extract_name` у дефолтов пуст, и с пустым `db_name` дефолты всех групп получили бы один ключ `('', '')` — фоновый MERGE оставил бы одну строку на все пакеты. Синхронизация проверяет это и отбрасывает такую строку-дефолт, не применяя её параметры.

Каждое поле разрешается по своему правилу:

| Поле | Как разрешается |
| :--- | :--- |
| `schema_name` | наследуется напрямую: своё непустое перебивает групповое |
| `params` | merge по ключам: умолчания `er_config.py` → группа → таблица |
| `schedule` | берётся групповое (см. ниже) |
| `description` | своё → комментарий таблицы в ClickHouse → групповое |
| `is_recent` | **не наследуется** |
| `pk`, `uk`, `fields`, `sql_from`, `sql_join`, `sql_where`, `sql_with`, `sql_settings` | **не наследуются** — всегда про конкретную таблицу |

**`description`** ставит групповой текст последним намеренно: иначе он затёр бы осмысленные комментарии всех таблиц пакета.

**`is_recent`** не наследуется, хотя это и не SQL: колонка `UInt8 DEFAULT 0`, и «не задано» от «явно delta» не отличить. При наследовании таблица в recent-группе не смогла бы вернуться к дельте — её `sql_stmt_export_delta` уехал бы под ключом recent.

**`schedule`.** Колонка имеет DDL-дефолт `'55 0 * * *'`, поэтому поставка, где расписание не задавали, всё равно возвращает это значение. Такое значение считается «не задано». Расписание пакета берётся из строки-дефолта, иначе — первое осознанно заданное среди поставок, иначе — `'55 0 * * *'`. Если у поставки задан свой отличный cron, в лог и заметку идёт предупреждение, но поставка остаётся в пакете: терять таблицу из-за косметики хуже, чем взять групповое расписание.

`is_active = 0` на строке-дефолте выключает группу целиком — вместе со всеми её поставками. Для этого синхронизация читает таблицу **без** фильтра по `is_active` и разбирается с ним уже в Python: иначе выключенная строка-дефолт просто исчезла бы из выборки, а поставки поехали бы дальше на умолчаниях из кода — где `notify_kafka = 1`, то есть стендовый пакет молча ушёл бы в ТФС.

### Колонки

| Колонка | Тип | Умолчание | Описание |
| :--- | :--- | :--- | :--- |
| `extract_name` | String | — | Имя выгрузки (table name без схемы); **пусто = строка-дефолт группы** |
| `db_name` | String | — | База данных источника; **у строки-дефолта = `replica`** |
| `replica` | String | — | Реплика с суффиксом группы; база до `__` ищется в `TFS_MAP` |
| `schema_name` | String | — | Целевая схема в `.meta`; наследуется |
| `pk` | Array(String) | `[]` | Первичный ключ |
| `uk` | Array(String) | `[]` | Уникальный ключ |
| `fields` | Array(String) | `[]` | SELECT-выражения. **Обязателен и явен**: `*` и `t1.*` запрещены |
| `sql_from` | String | `''` | FROM-часть: `"db.table"` или псевдоним CTE |
| `sql_where` | String | `''` | WHERE-условие: только бизнес-фильтр. Окно дельты фабрика дописывает сама |
| `sql_join` | String | `''` | JOIN-clause (полное выражение, включая ключевое слово) |
| `sql_with` | String | `''` | WITH-блок (CTE); вставляется перед SELECT |
| `sql_settings` | String | `''` | SETTINGS-блок ClickHouse |
| `params` | String | `'{}'` | JSON с переопределёнными параметрами |
| `description` | String | `''` | Описание; наследуется |
| `schedule` | String | `'55 0 * * *'` | Cron DAG-а группы; задаётся в строке-дефолте. Значение, равное DDL-дефолту, считается «не задано» |
| `is_recent` | UInt8 | `0` | `0` = delta, `1` = recent; **не наследуется** |
| `is_active` | UInt8 | `1` | `0` = запись игнорируется |
| `updated_at` | DateTime64(3) | `now64(3)` | Версия строки для ReplacingMergeTree; читать с `FINAL` |

### Валидация при синхронизации

Поставка не проходит валидацию (причина — в заметке `export_er_sync`, полный список в логе и в XCom `errors`), если:

- пустой `sql_from`;
- пустой `schema_name` (и своего нет, и в строке-дефолте нет) — иначе фабрика падает на разборе файла и уносит с собой **все** пакеты, а не только этот;
- базовая реплика не найдена в `TFS_MAP`;
- `fields` пуст или содержит `*` / `t1.*`;
- неизвестный `format` — проверяется по **слитым** параметрам (дефолты + группа + таблица), чтобы опечатка в строке-дефолте не доехала до фабрики.

Сюда же относится строка-дефолт группы с пустым `db_name`.

**Любая такая ошибка ломает весь пакет, а не одну поставку.** Тикет в ЕР один на группу, и уехавший неполный состав — это расхождение данных на стороне КАП. Вместо рабочего DAG появляется заглушка (см. ниже), а годные поставки группы в Variable не переносятся.

Расхождение `schedule` внутри пакета — не ошибка, а **предупреждение**: поставка остаётся, берётся групповое расписание, таск синка не краснеет. Иначе красный статус быстро обесценился бы.

### 🚦 Статус `export_er_sync`

- есть ошибки → таск **падает**. Иначе поломку в метаданных легко не заметить: раньше запись молча выкидывалась, а таск оставался зелёным;
- исправные группы при этом **всё равно записываются** в Variable — опечатка в одной строке не должна замораживать правки по остальным пакетам;
- в заметке: ошибки, предупреждения и сводка «N групп / M выгрузок» — одним блоком, ошибки первыми (`add_note` режет до 1000 символов);
- полные списки — в логе и в XCom: ключи `errors`, `warnings`, `summary`.

### 🚧 DAG-заглушка сломанного пакета

Сломанная группа попадает в Variable без таблиц, но с причинами и расписанием:

```json
"hrplatform_datalab__2": { "schedule": "0 4 * * *", "errors": ["…", "…"], "tables": {} }
```

Фабрика делает по такой записи DAG с тем же `dag_id` — `export_er__<replica>`, так что рабочий пакет **подменяется**, а не двоится:

- тег `BROKEN` и `❌` в описании — видно прямо в списке DAG-ов;
- полный перечень причин в `doc_md`;
- расписание группы сохраняется, а единственный таск `config_error` при запуске пишет причины в лог и в заметки и **падает**. Пакет продолжает сигналить красным раном в том же ритме, в каком должен был ходить;
- ранее работавший DAG при подмене остаётся включённым и начинает краснеть.

Если фабрика падает на чём-то, что валидация не поймала, цикл регистрации подставляет ту же заглушку с текстом исключения — одна битая группа не уносит остальные ER-пакеты.

### 🎛️ DAG Params (ручной запуск)

Состав намеренно скупой: **девять фиксированных параметров плюс по флагу на каждую таблицу пакета**. Все умолчания подобраны так, чтобы автозапуск (`schedule_next` → `trigger_dag(conf={})`) отработал обычный цикл дельты, не заполняя ни одного поля.

| Параметр | Умолчание | Что делает |
| :--- | :--- | :--- |
| `date_from`, `date_to` | пусто | Разовая выгрузка за период: `2026-08-01 00:00:00` либо `2026-08-01`. Задаются только вместе и в одном формате, состояние дельты не двигают |
| `is_current` | снято | Отметить — состояние считается актуальным, следующий цикл не запускается |
| `notify_kafka` | из группы | Отправлять ли уведомление в Kafka |
| `auto_confirm` | из группы | Не ждать квитанцию ТФС |
| `confirm_timeout` | из группы | Ожидание квитанции; сверху ограничен `execution_timeout` таска |
| `selfrun_timeout` | из группы | Задержка до следующего автозапуска |
| `max_file_size` | из стенда | Предел размера файла: `10GB`, `100MB` или число байт |
| `strategy` | пусто | Стратегия TFS на весь пакет; пусто = из настройки каждой таблицы |
| `tbl_<db>__<table>` | `True` | Грузить ли эту поставку в текущем ране |

**Флаги таблиц** — по одному чекбоксу на каждую поставку группы. Снятый флаг скипает всю TaskGroup таблицы: в ZIP и тикет она не попадёт, а её дельта останется на месте — `save_status` и `schedule_next` ходят по XCom и таблицу без него пропускают. Нужно, чтобы перелить одну сломавшуюся поставку, не гоняя весь пакет. Сняли все флаги — ран падает: пустой тикет ТФС от нас не ждёт. Побочный эффект, о котором стоит знать: ран с частью таблиц не взводит автозапуск за пропущенные.

**Чего в форме нет и почему.** Табличные настройки (`format`, `send_empty`, `pg_array_format`, `xstream_sanitize`, `sanitize_array`, `sanitize_list`, `increment`, `overlap`) живут в `er_wf_meta` и правятся дагом `export_er_wf_edit`. Как параметр пакета они применяли бы одно значение ко **всем** таблицам сразу — то есть чинили одну поставку и молча ломали остальные. По той же причине убраны `extract_time` и `condition`: состояние дельты у каждой таблицы своё и сохраняется в `extract_history`, а пакетный параметр сдвинул бы разом весь пакет.

## 🔀 Стратегии загрузки TFS

| Стратегия | Тип | UK | `ctl_action` из источника | Операция TFS |
| :--- | :--- | :--- | :--- | :--- |
| `APPEND` | INC | нет | любое (игнорируется) | `I` |
| `FULL_UK` | FULL | UK | любое кроме `D` | `I` |
| `FULL_UK` | FULL | UK | `D` | отброс |
| `FULL_NO_UK` | FULL | нет | любое кроме `D` | `I` |
| `FULL_NO_UK` | FULL | нет | `D` | отброс |
| `INC` | INC | UK | любое кроме `D` | `U` (есть запись) / `I` (нет) |
| `INC` | INC | — | `D` | `D` (есть запись) / отброс (нет) |

> При `FULL*`-стратегиях TFS предварительно удаляет все записи snp, затем загружает новые. Строки с `ctl_action=D` отбрасываются.

## ✏️ Правка настройки из UI

Даг `export_er_wf_edit` (`er_wf_edit.py`) заводит новые записи и правит существующие,
чтобы не ходить в `clickhouse-client`. Три параметра:

| Параметр | Смысл |
| :--- | :--- |
| **Запись** | `➕ новая запись` либо ключ существующей из выпадающего списка |
| **Патч** | JSON **только с изменяемыми полями**; для новой записи — вся запись |
| **Синхронизировать** | Запустить `export_er_sync` после успешной записи |

Поменять расписание группы — `{"schedule": "30 2 * * *"}`. Выключить запись —
`{"is_active": 0}`; у строки-дефолта это гасит весь пакет. Отдельной кнопки удаления нет.

**Почему два поля, а не одно.** Параметр с `examples` Airflow рендерит выпадающим списком
**вместо** свободного поля, а подставить выбранное значение в соседнее поле статическая
форма не умеет. Поэтому выбор и правка разведены: список говорит, *какую* запись берём,
патч — *что* в ней меняем. Копировать весь JSON записи при этом не нужно.

**Список записей** строится при разборе файла из Variable `datalab_er_wf_meta`, которую
попутно наполняет `export_er_sync` (сырые строки таблицы, включая выключенные). В ClickHouse
на каждом парсинге не ходим — это лишняя нагрузка и Broken DAG при недоступности базы.
Следствие: запись, созданную только что, список покажет после ближайшего синка.

**Проверки — те же, что у синка**: непустой `sql_from`, реплика в `TFS_MAP`, непустой
`schema_name`, явный `fields` без звёздочки, известный `format`, а у строки-дефолта —
`db_name`, равный `replica`. Не прошло — таск красный и в таблицу ничего не записано:
ошибку видно там, где её сделали, а не через два дага. Ради этого валидация вынесена
из `er_sync.py` в `er_config.py` — импортировать файл с DAG-ом ради хелпера нельзя.

Обратное тоже верно, и поэтому даг лежит отдельным файлом, а не в `er_config.py`:
`_process_modules` добавляет к найденным дагам `DagContext.autoregistered_dags`, куда
попадает всё созданное декоратором `@dag` за время разбора текущего файла. Конфиг
импортируют три модуля — даг из него привязался бы к каждому. **Модуль, который
импортируют DAG-файлы, сам DAG-и создавать не должен.**

Освободить имя `er_config.py`, переименовав конфиг в `er_common.py`, нельзя: в проде
всё разворачивается в пакет `CI06932748.analytics.datalab.export_er/`, где `er_common.py`
занят легаси-модулем старого ER.

Правка существующей записи — это **вставка новой версии**: `ReplacingMergeTree` схлопнет
её по `(db_name, extract_name)` при фоновом MERGE. В заметке к прогону остаётся диф
«поле: было → стало».

## ➕ Как завести новый пакет

### 1. Строка-дефолт группы

```sql
INSERT INTO export.er_wf_meta (extract_name, db_name, replica, schema_name, schedule, description, params)
VALUES (
    '',                          -- пусто → строка-дефолт
    'hrplatform_datalab__1',     -- = replica: держит ключ (db_name, extract_name) уникальным
    'hrplatform_datalab__1',
    'target_schema',
    '55 0 * * *',
    'Пакет 1: справочники обучения',
    '{"auto_confirm": 0, "max_active_tasks": 2}'
);
```

### 2. Поставки группы

```sql
INSERT INTO export.er_wf_meta
    (extract_name, db_name, replica, uk, fields, sql_from, sql_where, params)
VALUES (
    'my_table',
    'my_database',
    'hrplatform_datalab__1',
    ['id'],
    ['id', 'name', 'updated_at'],   -- явный список обязателен
    'my_database.my_table',
    '',
    '{"strategy": "FULL_UK"}'
);
```

### Поставка с JOIN

При непустом `sql_join` состав `fields` особенно важен: без него `*` развернулось бы в колонки обеих таблиц, и дубли справа (`t2.col`) уехали бы в CSV и в `.meta`.

```sql
INSERT INTO export.er_wf_meta
    (extract_name, db_name, replica, uk, fields, sql_from, sql_join, sql_where, params)
VALUES (
    'my_table',
    'my_database',
    'hrplatform_datalab__1',
    ['id'],
    ['t1.id', 't1.name', 't2.flag'],
    'my_database.my_table t1',
    'LEFT JOIN my_database_export.my_table_exp t2 ON t1.id = t2.id',
    '',
    '{"strategy": "FULL_UK"}'
);
```

### Тяжёлый запрос с CTE и SETTINGS CH

```sql
INSERT INTO export.er_wf_meta
    (extract_name, db_name, replica, uk, fields,
     sql_with, sql_from, sql_where, sql_settings, params)
VALUES (
    'my_heavy_table',
    'my_database',
    'hrplatform_datalab__1',
    ['id'],
    ['id', 'updated_at'],
    'WITH cte AS (SELECT id, max(updated_at) AS updated_at FROM my_database.my_heavy_table GROUP BY id)',
    'cte',
    '',
    'max_threads=2, max_memory_usage=10000000000',
    '{"strategy": "FULL_UK"}'
);
```

### 🔄 Recent-режим

```sql
INSERT INTO export.er_wf_meta
    (extract_name, db_name, replica, uk, fields, sql_from, is_recent, params)
VALUES (
    'my_table',
    'my_database',
    'hrplatform_datalab__2',
    ['id'],
    ['id', 'progress'],
    'my_database.my_table',
    1,
    '{"recent_interval": 120}'
);
```

> Для recent-режима `sql_where` не нужен — условие формируется автоматически по `time_field`.

## 🛠️ Технические детали

- 🔍 **Сверка состава колонок**: `build_meta` сравнивает результат `DESCRIBE` итогового запроса с именами из `fields` и падает при расхождении. Смысл — новая колонка в источнике не доезжает до КАП сама, только через правку настройки. Имя выводится из выражения, если у него есть явный алиас (`expr as name`) или это простая колонка (`t1.col`); для выражений без алиаса (`cast(x as String)`) имя предсказать нельзя, такая позиция сверяется только по количеству, а в лог идёт предупреждение с предложением добавить алиас.
- 🔤 **Hive reserved words**: `build_meta` добавляет суффикс `_` к именам колонок, совпадающим с зарезервированными словами Hive (все версии 1.2–4.0).
- 📭 **send_empty**: задаётся только в `er_wf_meta`, параметра запуска у него нет. При `send_empty=1` и нулевой дельте `pack_zip` создаёт ZIP с пустым файлом данных + TKT + META. Соответствует требованию TFS: «пустой пакет выгружается по расписанию даже при отсутствии изменений».
- 🔄 **Синхронизация**: `export_er_sync` расписания не имеет — только ручной Trigger DAG после правки `export.er_wf_meta`.
- 🏊 **Pools**: `datalab_export_er` (20 слотов) создаёт `export_er_sync`; пул отправки `tfs_send` (1 слот) — уже забота `tfs_kafka` (заводит `tfs_kafka_rcv`). Прежние `tfs_<scenario>` не нужны — требование «не передаётся несколько пакетов одновременно» выполняет сам `tfs_kafka_snd`; уже созданные можно удалить руками.
- 💧 **Стриминг**: ZIP-архивация потребляет минимум памяти — `stream_zip` + multipart-загрузка в S3 без буферизации всего файла.
- 🔒 **Изоляция**: фреймворк не зависит от общих `plugins`, используя собственные хелперы в `er_config.py`.
- ✅ **Идемпотентность**: `export_er_sync` записывает Variable только если данные изменились.
- 📝 **on_callback**: при падении таска добавляет заметку с трейсом в Airflow UI на уровне Task и DAG Run; при успехе — на уровне Task.

## 🔧 Переход со схемы «одна таблица — один DAG»

Структура `export.er_wf_meta` не меняется — правятся только данные.

1. Заполнить `fields` у действующих поставок (раньше пустой список означал «все колонки») — запрос-генератор в `er_wf_meta.sql`. Он отдаёт состав в порядке DDL источника, то есть ровно тот, что уезжает в `.meta` сегодня.
2. Проставить поставкам `replica` с суффиксом группы.
3. Добавить строки-дефолты групп: `extract_name = ''`, `db_name = replica`.
4. Прогнать `export_er_sync`, сверить Variable `datalab_er_wfs`. При ошибках таск краснеет, причины — в заметке, полные списки в логе и в XCom.
5. Включить новые DAG-и `export_er__<replica>` — они создаются на паузе. Старые `export_er__<schema>__<table>` исчезнут сами.

История дельты переезд переживает: она привязана к `extract_name` в `export.extract_history`.
