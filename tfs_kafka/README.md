# 📡 Тракт Kafka ↔ ТФС
*2026-08-13 13:33 MSK · v1.3 · Чуркин Николай · [nschurkin@sber.ru](mailto:nschurkin@sber.ru)*

Приём обратных квитанций и отправка уведомлений с соблюдением темпа. Общий контур:
сейчас им пользуется ЕР, следующим переезжает xStream.

Конфигурация, утилиты и хранилище тракта живут в `plugins/tfs_utils.py` — не рядом
с дагами. Причина та же, по которой там же лежат `ctl_utils` и `ctl_core`: модулем
пользуются **два** каталога, `tfs_kafka` и `er_export`. Держать настройку у одного
из них значило бы либо связать каталоги, либо развести её по копиям.

Копии тут недопустимы принципиально: если приёмник запишет квитанцию в одно место,
а `wait_confirm` пойдёт искать её в другое, пакет зависнет до таймаута и причина не
будет видна ниоткуда. Поэтому источник истины ровно один — S3.

🔗 Единственная связь с `er_export` — имена двух таблиц, продублированные в обоих
конфигах. Менять синхронно.

## Зачем это отдельно

ТФС отвечает на каждое уведомление обратной квитанцией, но кладёт её **в общий топик
по всем маршрутам сразу** (сейчас `TFS.HRPLT.OUT`). Сопоставление — по `RqUID`, результат
передачи — в `Status/StatusCode` (`0` = успех).

Топиков может быть несколько: список в `KAFKA_RCV_TOPICS` (`plugins/tfs_utils.py`),
на каждый заводится свой таск-сенсор. Из какого топика пришла квитанция, видно
в колонке `kafka_topic`.

Kafka раздаёт сообщение одному потребителю в группе. Значит, читать этот топик из
выгрузок нельзя: кто первым вычитал — тот и забрал, а настоящий адресат ждёт вечно.
Именно так и было до этого дага — ожидание в ER брало **любое** сообщение из топика,
подтверждало им свой пакет, съедало чужую квитанцию и не смотрело на `StatusCode`.

Поэтому потребитель ровно один: `tfs_kafka_rcv`. Он ничего не решает — просто
складывает всё, что пришло, в хранилище тракта. Ждут своих квитанций уже сами выгрузки.

```
ТФС → Kafka (KAFKA_RCV_TOPICS) → tfs_kafka_rcv → хранилище тракта
                                                        ↑
                           выгрузка ждёт свой RqUID ────┘
```

## ⏱️ Оба дага — сенсоры с часовым окном

`tfs_kafka_rcv` и `tfs_kafka_snd` устроены одинаково: `@task.sensor` в режиме
`reschedule`, опрос раз в 15 секунд, окно — час. Между опросами слот воркера свободен,
так что час ожидания ничего не занимает.

Итог окна виден по цвету таска, без открывания логов:

| Что было за час | Таск |
| :--- | :--- |
| пришли квитанции / ушли файлы | ✅ зелёный, их число в XCom результата |
| тишина | ☮️ скипнут (`soft_fail`) |
| очередь стоит дольше `TFS_QUEUE_ALERT_MIN` | ❌ падение с текстом затора |

Окно держится до конца намеренно: квитанция на пятой минуте не должна обрывать чтение
на оставшиеся пятьдесят пять. Счётчик за окно переживает опросы объектом в `state/`
(см. ниже) — процесс между ними умирает, а XCom Airflow стирает перед каждым запуском.

Партиции берутся `assign()`, а не `subscribe()`: подписка вступала бы в группу заново
каждые 15 секунд, а ребаланс задевает и соседние топики той же группы. `OFFSET_STORED`
оставляет чтение с коммиченной позиции.

## 🗄️ Где хранятся данные

**S3 — источник истины.** Туда идёт каждая запись, оттуда идёт **каждое** чтение:
писатель и читатель обязаны смотреть в одно место, иначе пакет зависает без объяснений.
ClickHouse и Postgres — зеркала: пишем в них, если задан conn_id, и нужны они только
чтобы смотреть на тракт запросами.

| Хранилище | Включается | Роль | Что лежит |
| :--- | :--- | :--- | :--- |
| S3 | всегда | источник истины: пишем и читаем | объекты рядом с логами |
| ClickHouse | непустой `CH_ID` | зеркало, только запись | `export.tfs_receipts`, `export.er_sent_files` |
| Postgres / Greenplum | непустой `PG_CONN` | зеркало, только запись | те же таблицы, DDL `*_pg.sql` |

Сбой зеркала **не роняет тракт**: к этому моменту запись в S3 уже прошла, и терять
квитанцию из-за аналитической копии нельзя. В лог уходит предупреждение, расхождение
лечится дозаливкой. Ошибка самого S3, наоборот, прокидывается.

Путь для S3 не задаётся отдельно: берётся из `airflow.cfg` — `remote_base_log_folder`
и `remote_log_conn_id`, поэтому на каждом стенде бакет и коннект верные сами собой.
Раскладка под `{логовый бакет}/tfs/`:

```
receipts/{rq_uid}.json                                    квитанция целиком
queue/pending/{rq_uid}.json                               ждёт отправки
queue/sent/{YYYYMMDD}/{scenario}/{rq_uid}__{HHMMSS}.json  отправлено
state/{YYYYMMDD}/{dag}__{task}__{run_id}.json             память сенсора за окно
```

**Про `state/`.** Счётчик окна и признак «параметры запуска уже разобраны» лежат объектом,
а не в XCom, и это не прихоть: в режиме `reschedule` каждый опрос — отдельное исполнение
таска, а Airflow перед запуском зовёт `clear_xcom_data()` и стирает весь XCom этого таска
за ран. Записать под соседний `task_id` тоже нельзя — у таблицы `xcom` внешний ключ на
`task_instance`. Проверено живьём: до этой правки ручная досылка ставила файлы в очередь
на **каждом** опросе — два файла превращались в десять.

**`RqUID` — префикс имени, а не хвост.** Все три вопроса тракта задаются по нему
(«есть квитанция?», «ещё в очереди?», «куда переносить при отправке?»), и с `RqUID`
в начале каждый решается точечным обращением к ключу вместо обхода префикса. Так с
самого начала был устроен `receipts/` ради `wait_confirm` — очередь приведена к тому же
виду: `mark_sent` больше не листает `pending/`, чтобы найти строку по суффиксу.

**Дата в пути `sent/` идёт перед сценарием** — и это тоже не косметика:

- счётчики лимитов листают только папки за сегодня и вчера, а не весь архив отправок,
  который никто не чистит и который растёт вечно;
- диагностика по `RqUID` не знает сценария, зато знает дату — и с датой впереди ей
  хватает тех же двух папок сразу на все маршруты.

Время отправки при этом остаётся **в имени** ключа: окна считаются по именам, без чтения
объектов. Скользящее суточное окно всегда укладывается в две соседние даты.

Сверх этого сам отправитель спрашивает расход лимитов **один раз на маршрут за опрос**,
а дальше считает свои отправки в памяти (стареют они через тот же `window_hits`). Раньше
счётчик запрашивался на каждый файл очереди — на S3 это давало листинг на строку.

У `pg` своя особенность: `ON CONFLICT` не используется, потому что в Greenplum 6 (ядро
PG 9.4) его нет. Дубли допускаются при записи и снимаются при чтении через `DISTINCT ON` —
тот же принцип, что `FINAL` в ClickHouse. По той же причине очередь append-only:
отметка отправки дописывает строку, а не делает `UPDATE`.

## Как работает

Ран живёт час, `max_active_runs=1`. Опрос читает топик, пока идут сообщения, и
заканчивается по тишине (5 секунд) либо по потолку в 5000 сообщений за опрос;
следующий опрос — через 15 секунд. Следующий ран создаётся по расписанию, ждёт
в `queued` и стартует сразу, как текущий закончился.

**Порядок операций важен:** сначала запись в хранилище, только потом коммит offset.
При обратном порядке падение между операциями потеряло бы квитанцию навсегда — а её ждёт
выгрузка. Обратная сторона: at-least-once, то есть возможен повтор. Его схлопывает
`ReplacingMergeTree` по `(rq_uid, file_name)`; читать с `FINAL`.

**Битое сообщение не роняет ран** — сохраняется с `status_code = -1` и исходным текстом
в `raw_xml`. Потерять квитанцию хуже, чем сохранить её неразобранной, а застрявшее
сообщение заблокировало бы очередь всем остальным.

**Ненулевой `StatusCode` здесь только логируется.** Это не проблема сборщика: ошибку
покажет та выгрузка, которая ждёт эту квитанцию, — у неё есть контекст пакета.

## Кто ещё трогает этот топик

Никто не должен. Единственный законный конкурент — `tools_test_kafka_rcv` в режиме
`wait` (`ctl/check/test_kafka.py`): он работает в той же consumer group и уводит
сообщения. Запускать его на `TFS.HRPLT.OUT` можно только при остановленном
`tfs_kafka_rcv`. Для разбора инцидентов обычно достаточно `export.tfs_receipts`.

## Диагностика

```sql
-- неуспешные передачи за сутки
SELECT rq_tm, scenario_id, file_name, status_code
FROM export.tfs_receipts FINAL
WHERE status_code != 0 AND received_at >= now() - INTERVAL 1 DAY
ORDER BY received_at DESC;

-- сообщения, которые не разобрались
SELECT received_at, kafka_partition, kafka_offset, substring(raw_xml, 1, 500)
FROM export.tfs_receipts FINAL
WHERE status_code = -1 ORDER BY received_at DESC;
```

Отправлено, но квитанции нет (по данным ЕР) — джойн с реестром отправок:

```sql
SELECT s.file_name, s.notified_at
FROM export.er_sent_files FINAL AS s
LEFT ANTI JOIN export.tfs_receipts FINAL AS r USING (rq_uid)
WHERE s.notified_at > toDateTime64(0, 3)
  AND s.notified_at < now() - INTERVAL 1 HOUR;
```
