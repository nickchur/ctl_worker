# Проект: ctl_worker

## Что это

Репозиторий DAG'ов и общих модулей Apache Airflow для управления ETL-процессами HR-платформы.
Внутри — семь независимых проектов, по одному на каталог; общий у них только рантайм (один
Airflow) и папка `plugins/`, из которой остальные берут утилиты.

| Каталог | Что делает | Спецификация |
| :--- | :--- | :--- |
| `ctl_worker/` | Оркестрация загрузок через CTL API: генерация DAG'ов, сенсор, монитор, события | `specs/ctl-worker/` |
| `plugins/` | Общие модули: конфигурация, обёртки API и БД, S3, утилиты Airflow, тракт ТФС | `specs/plugins/` |
| `er_export/` | Выгрузка ЕР: ClickHouse → S3 → уведомление в ТФС | `specs/er-export/` |
| `tfs_kafka/` | Тракт Kafka ↔ ТФС: отправка уведомлений и приём квитанций | `specs/tfs-kafka/` |
| `xs_export/` | Выгрузки xStream, генерируемые из JSON-метаданных | `specs/xs-export/` |
| `tools/` | Служебные DAG'и ручного запуска (в основном S3) | `specs/tools/` |
| `check/` | Проверка подключений, операторов и обслуживание метабазы | `specs/check/` |

## Стек

- Python строго `>=3.9, <3.10`, Apache Airflow 2.10.1, SQLAlchemy 1.4.x
- Greenplum 6.x (`psycopg2`, доступ по Kerberos/GSSAPI), ClickHouse, S3 (`boto3`), Kafka
- Платформенный пакет `sber_app_dataplatform_etl_core`: операторы `hrp_operators`,
  secret backend, из которого приходят все connections
- Линтер `ruff`, `line-length=120`, target py39

## Соглашения

- **Строка версии.** Вторая строка docstring любого модуля: дата-время MSK, версия, автор.
  Поднимается при каждой правке, кроме правок из одних комментариев.
- **Заметки вместо почты.** Канал сообщений на контуре — `add_note(data, context,
  level='task|DAG', title=...)` и падение таска; почтовых рассылок нет.
- **Статусы в сводках:** ✅ success / ❌ failed / ☮️ skipped.
- **SQL-идентификаторы** валидируются через `validate_identifier` — защита от инъекций.
- **Контракт `(status, payload)`.** Функции-решатели (`ctl_chk_*`, `pause_set`, `store_params`)
  возвращают пару, а не бросают исключение; разбирает её вызывающий таск (`raise_status`).
  На исключениях остаются только транспортные функции.
- **Двойной импорт plugins.** DAG'и импортируют модули с fallback, потому что на боевых
  контурах пакет лежит по другому пути:
  ```python
  try:
      from plugins.ctl_core import chk_any_conn
  except ImportError:
      from CI06932748.tools.utils import chk_any_conn
  ```
- **Ленивая инициализация.** `get_config()` и список S3-бакетов читаются при первом
  обращении, а не на импорте: парсинг DAG'а не должен ходить в сеть и падать без Variable.

## Как пользоваться спецификациями

- Спека отвечает на «что система обязана делать», `readme.md` каталога — на «как устроено».
  Дублировать одно в другом не нужно: разойдутся.
- Правка поведения начинается с предложения (`/opsx:propose`), а не с кода.
- Проверка: `openspec validate --all --strict`, список — `openspec list --specs`.
