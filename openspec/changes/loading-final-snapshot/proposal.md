# Итог загрузки сохраняется, а не только состояние на входе

## Why

В S3 по каждой загрузке лежит ровно один снимок — `ctl_working/{lid}.json`, и пишет его
проверка состояния, которая идёт в начале каждого шага. Каждый шаг перезаписывает файл,
поэтому в нём остаётся состояние на вход в последний шаг. Того, чем загрузка кончилась —
финального статуса, лога с результатом, признака завершения, времени пробуждения при
повторе, — не сохраняется нигде.

Для разбора инцидента это половина картины: видно, с чем загрузка входила в завершающий
шаг, но не видно, что записал CTL после финализации. Восстановить это позже неоткуда:
CTL держит историю ограниченное время, а наши снимки живут неделю.

Лишний запрос к CTL для этого не нужен: вызовы, которые ставят финальный статус и
завершают загрузку, возвращают ответ API — сейчас он просто отбрасывается.

## What Changes

- После финализации статуса сохраняется снимок загрузки, каким её видит CTL, — отдельно
  от снимка на входе в шаг.
- Снимки разных попыток не затирают друг друга: цепочка «ошибка → ожидание повтора →
  итог» видна целиком.
- Снимок кладётся до ветвления на пропуск и падение, иначе для самых интересных исходов
  не сохранялось бы ничего.
- Неудача сохранения не меняет исход загрузки: она уже финализирована в CTL, и красный
  таск после этого противоречил бы её статусу.

## Capabilities

### New Capabilities

Новых capability нет.

### Modified Capabilities

- `ctl-worker`: итог загрузки сохраняется в S3 отдельно от состояния на входе в шаг.

## Impact

- Спецификация: `ctl-worker`
- Код: `ctl_worker/ctl_worker.py`, `plugins/ctl_core.py`
- Хранилище: новый префикс в бакете CTL; отдельный срок хранения не нужен — правило
  бакета выставляется без префикса и покрывает его
- Документация: `ctl_worker/readme.md`
