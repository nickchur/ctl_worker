# Часть A. Пауза отправки в ТФС

## Контекст

Григорий Середнев просит уметь **приостанавливать отправку** очереди — на технические
работы, выкладку доработок, сбой на стороне ТФС. Выгрузка в S3 и постановка в очередь
должны при этом идти по расписанию (выгрузка длинная и дорогая), очередь — копиться,
а после снятия паузы уехать сама. Уровни: конкретная поставка, группа/реплика, маршрут.

Там же два его вопроса:

* **Подтверждение.** Сейчас `_er_wait_confirm` ждёт квитанции по своим `RqUID` до
  `confirm_timeout` (групповой параметр, по умолчанию 60 мин, правится и в форме запуска;
  сверху ограничен `execution_timeout` = таймаут + 5 мин) и падает по истечении, различая
  «очередь стоит» и «отправлено, ответа нет». Любой `StatusCode != 0` роняет таск сразу.
  Таймаут настраиваемый — это уже так.
* **Retry.** Забранный ТФС файл переотправить нельзя, оставшийся в бакете — можно.
  Сейчас `enqueue_files` не проверяет наличие объекта вовсе: опечатка в имени уезжает
  в ТФС и возвращается квитанцией с кодом 101/108. Проверка бакета и есть тот самый
  различитель «можно retry / нельзя».

Сегодня выключателей два, и оба грубые: пауза дага `tfs_kafka_snd` (встаёт весь тракт,
все маршруты) и удаление пула `tfs_<ScenarioId>` (маршрут выпадает из реестра, работает
только на разобранной очереди, сценарии из `TFS_ROUTES` так не выключить).

Выбранные решения: правила паузы — маршрут + реплика + пакет; `wait_confirm` на паузе
**скипается**; состояние — в Variable `tfs_snd_pause`; досылка получает проверку бакета.

## A1. `plugins/tfs_utils.py` (v1.13 → v1.14) — состояние паузы

```python
PAUSE_VAR = 'tfs_snd_pause'
```

Формат — три раздела, в каждом `{ключ: правило}`; правило либо строка-причина,
либо объект `{"until": ISO, "reason": …, "by": …}`:

```json
{
  "scenarios": {"HRPLATFORM-4000": {"until": "2026-09-01T22:00:00+03:00", "reason": "техработы ТФС"}},
  "replicas":  {"hrplatform_datalab__1": "внедрение доработок"},
  "packages":  {"hrplatform_datalab__1__20260828120000": "разбираемся с отказом"}
}
```

Новые функции:

* `pause_rules() -> dict` — читает Variable, нормализует строку/объект к одному виду,
  выбрасывает истёкшие по `until` и неразобранные правила с предупреждением в лог.
  **Ничего не бросает** — как `saved_params` в `plugins/utils.py`: битая переменная
  означает «паузы нет», а не остановку тракта.
* `package_key(row) -> str` — `{replica}__{14 цифр package_ts}`. Ровно тот ключ, что уже
  строит `_package_key` в `tfs_kafka_snd`; функция переезжает сюда, и один формат служит
  и ключом XCom, и ключом паузы.
* `pause_reason(row, rules=None) -> str` — пусто, если строке можно ехать; иначе готовый
  текст. Порядок от частного к общему (пакет → реплика → маршрут), чтобы в сообщении
  стояло самое конкретное правило.
* `split_pending(rows, rules=None) -> tuple[list, list]` — `(свободные, придержанные)`;
  отправитель и проверка затора обязаны делить очередь одинаково.
* `stale_sent(minutes) -> list[dict]` — отправленные больше `minutes` назад, у которых нет
  квитанции. Читает `queue/sent/{сегодня,вчера}/…` (те же две папки, что `_s3_sent_counts`)
  и проверяет наличие `receipts/{rq_uid}.json`. Нужна именно из-за скипа `wait_confirm`:
  пока пакет на паузе, его квитанции не ждёт никто.
* `pause_set(scope, key, until='', reason='', by='')` и `pause_clear(scope, key)` —
  правка переменной для дага-пульта (A6). Возвращают **`(status, message)`** со статусом
  `ok` / `skip` / `fail`, как `store_params` в `plugins/utils.py`: решение о скипе или
  падении принимает таск, там же, где стоят `trigger_rule` и текст для UI. Правило
  добавляется и снимается точечно, остальные разделы переменной не трогаются.
* `pause_summary(rows=None) -> dict` — что сейчас на паузе и что из очереди этим
  придержано: правила по разделам плюс счётчики придержанных строк.

`get_config()` отдаёт `PAUSE_VAR` и `TFS_STALE_MIN`.

## A2. `plugins/tfs_utils.py` — проверка бакета при досылке

В `TFS_ROUTES` у маршрута появляются `conn`, `bucket`, `prefix` (`s3-tfs-hrplt` /
`tfshrplt` / `from/KAP802/hrpl_lm_er` для `HRPLATFORM-4000` — те же значения, что
`S3_CONN`/`BUCKET`/`TFS_MAP` в `er_config.py`; копия осознанная, фабрика ЕР намеренно
не импортирует `tfs_utils` на уровне модуля).

`enqueue_files(...)` возвращает **`(поставленные, пропущенные)`** и перед постановкой
проверяет `check_for_key` в бакете маршрута. Пропущенные — с причиной: «нет в
`s3://tfshrplt/from/…/имя` — либо ТФС уже забрал файл, либо опечатка». У маршрута без
описанного бакета проверки нет (предупреждение в лог), досылка идёт как раньше.
Call site ровно один — `_enqueue_params_once` в `tfs_kafka_snd`.

## A3. `tfs_kafka/tfs_kafka_snd.py` (v2.6 → v2.7)

* `poke_queue`: после отбора своих строк — `free, held = split_pending(queued)`; едет
  только `free`. Придержанное **не попадает в `left`**, по которому считается затор:
  иначе осознанная пауза каждый час роняла бы таск по `TFS_QUEUE_ALERT_MIN`. Это ключевая
  правка — без неё пауза выглядит как авария.
* Заметка о паузе — один раз за окно (флаг в `run_state_*`, как `PARAMS_KEY`), а не каждые
  15 секунд; в `return_value` добавляется `held` — придержанное видно в UI без логов.
* `_finish`: в текст затора добавляется, сколько строк придержано и по какому правилу.
* `poke_scan`: разбирает `(rows, missing)` от `enqueue_files` и показывает пропущенные
  отдельной строкой заметки; раз в час (последний опрос окна) зовёт `stale_sent` и
  предупреждает о неподтверждённых.
* Реестр сценариев пауза не трогает: `drop_unpooled_scenarios` смотрит на пул, пул на месте.

## A4. `er_export/er_export.py` (v3.15 → v3.16)

Проверок паузы ровно две, и обе **вне** цикла ожидания:

* **На входе** — `_pre_await(gcfg, context)` (сейчас `_pre_await(context)`, call site один)
  получает четвёртую причину скипа: пакет уже на паузе, ждать нечего, час занятого слота
  в `datalab_export_er` ни к чему. Строка для `pause_reason` собирается из
  `gcfg['scenario']`, `gcfg['replica']` и метки `_pkg_ts(context)`.
* **На выходе по таймауту** — вместо нынешнего безусловного падения: если правило паузы
  совпало, таск уходит в ☮️ с текстом «квитанций нет, пакет придержан паузой: …»;
  не совпало — падает как раньше, с разбором «очередь стоит / ответа нет».

Внутри цикла паузу **не опрашиваем** намеренно. Пауза, поставленная и снятая за тот же
час, пакета не касается: файлы уедут в том же окне, квитанции придут, цикл закончится
зелёным — а проверка в цикле погасила бы такой пакет на ровном месте. Побочно это
экономит поход в метабазу каждые 10 секунд на каждом ждущем пакете
(см. `project_pg_session_timeouts`): чтений становится два на таск вместо сотен.

Следствие скипа, которое надо назвать вслух в доке: `save_status` отработает
с `confirmed = null`, дельта сдвинется, `schedule_next` продолжит цикл — красных ранов
пауза не даёт, но и подтверждения по этим файлам никто не ждёт. Дыру закрывает
`stale_sent` из A3.

## A5. Новый даг-пульт `tfs_kafka/tfs_kafka_setup.py` (v1.0)

Пульт паузы по образцу `er_export/er_setup.py`: форма запуска → показ состояния →
правка → показ результата. Руками редактировать JSON переменной в UI не придётся,
а неверный ключ или битый `until` не доедет до отправителя.

`schedule=None` (только ручной запуск), `max_active_runs=1`, пул `default_pool` —
пульт не должен занимать слоты тракта.

**Форма:**

| Параметр | Что задаёт |
| :--- | :--- |
| `action` | `👁️ показать` *(по умолчанию)* / `⏸️ поставить на паузу` / `▶️ снять с паузы` / `🧹 убрать истёкшие` |
| `scope` | `scenario` (маршрут) / `replica` (группа) / `package` (один пакет) |
| `key` | значение ключа: `HRPLATFORM-4000`, `hrplatform_datalab__1`, `hrplatform_datalab__1__20260828120000` |
| `until` | до какого времени, ISO; пусто — бессрочно |
| `reason` | зачем — попадает в правило и в заметку |

`key` — свободная строка, а не `enum`: реплики и пакеты живут в очереди, а её читать
на разборе DAG-файла нельзя (это поход в S3). Откуда копировать значение, показывает
таск `show`.

**Таски:**

* `show` — текущие правила (`pause_summary`) плюс сводка очереди: сколько строк ждёт,
  сколько из них придержано и каким правилом, какие сценарии/реплики/пакеты в очереди
  вообще есть. Работает и сам по себе — это и есть `action = показать`.
* `apply` — зовёт `pause_set` / `pause_clear` / чистку истёкших и разбирает статус явно,
  как таск `params` в `check/db_cleanup.py`:
  `skip` (`action = показать`, правило уже такое, снимать нечего) → `AirflowSkipException`,
  `fail` (пустой ключ, `package`-ключ не того формата, `until` не разобрался) →
  `AirflowFailException`.
* `after` — состояние после правки, `trigger_rule=NONE_FAILED` (обязательно: `apply`
  штатно скипает себя, а дефолтный `ALL_SUCCESS` утянул бы в скип и показ результата —
  на этом уже спотыкались в `db_cleanup`).

## A6. `_ch_mark_sent` теряет `dag_id` и `run_id` (найдено при разборе задания)

В ClickHouse-зеркале отметка отправки дописывает новую версию строки
`INSERT … SELECT` **без колонок `dag_id` и `run_id`**, а `ReplacingMergeTree` по ключу
`rq_uid` оставляет последнюю версию — после `mark_sent` оба поля пустые. При постановке
в очередь они записаны, в Postgres-зеркале перечислены, в S3 (источник истины) объект
переносится целиком: расхождение только в ClickHouse и только у уже отправленных файлов.
Лечится добавлением двух колонок в `INSERT … SELECT`.

## Чего не делаем (A)

* Пауза на отдельную таблицу пакета: тикет перечисляет все архивы пакета, задержать часть

  только паузой.

## Риски (A)

* **Забытая пауза** — очередь растёт молча, алерт затора по ней намеренно выключен.
  Поэтому `until` в правиле, сводка придержанного в заметке каждого рана и предупреждение
  в логе на каждом опросе.
* **Длинная пауза упирается в суточный лимит**: маршрут отдаёт 2000 файлов в сутки,
  500 в час — накопленное за сутки простоя за один час не уедет. Сказать в README.
* Пакеты, уехавшие «вслепую» (скипнутый `wait_confirm`), видны только через `stale_sent`.

# Часть B. Пересоздание `er_wf_meta`: ключ `(replica, dag_group, schema_name, extract_name)`

> Правки задания от 28.08.2026 (после первой реализации): группа вынесена из `replica`
> в отдельную колонку `dag_group`, `schema_name` вошёл в ключ, добавлен `is_paused`,
> убран `db_name`, состояние дельты ключуется составным именем `<dag_id>.<extract_name>`.

## Контекст

Четыре вещи, растущие из одного корня:

1. **Группа кодировалась суффиксом в `replica`** (`hrplatform_datalab__1`) — и её приходилось
   всюду отрезать (`replica_base`, `replica_group`, `replica_full`). Теперь это отдельная
   колонка `dag_group`.
2. **`db_name = replica` у строки-дефолта** — костыль под старый `ORDER BY (db_name, extract_name)`.
   Признаком группы должен быть **пустой `extract_name`**, и только он.
3. **Одна таблица в двух группах невозможна** — нельзя завести новую версию пакета,
   не убив старую.
4. **Расписание жило в трёх местах**: строка-дефолт, любая поставка, код.

Совместимость не нужна — таблица **пересоздаётся**.

## B1. `er_export/er_wf_meta.sql` (v1.2 → v3.0) — новая таблица

```
replica, dag_group, schema_name, extract_name, description, is_active, is_paused,
pk, uk, fields, sql_from, sql_where, sql_join, sql_with, sql_settings, params, updated_at
ENGINE = ReplicatedReplacingMergeTree('/clickhouse/tables/er_wf_meta_{uuid}', '{replica}', updated_at)
ORDER BY (replica, dag_group, schema_name, extract_name)
```

* `dag_group` — группа поставок, она же часть `dag_id` и часть имени архива. Пустая
  нормализуется к `'0'`: в имени файла разделителей `__` должно быть одно и то же число
  у всех пакетов.
* `schema_name` в ключе: одна и та же таблица может приезжать в разные целевые схемы.
* **`db_name` убран совсем.** База источника выводится из `sql_from` маской `db.table`
  (см. `sql_sources`), а там она пишется всегда. Плата: если в `sql_from` базы нет вовсе
  (неквалифицированное имя), описания колонок в `.meta` просто не найдутся —
  с предупреждением в логе, но без ошибки.
* **`is_paused`** — новая колонка, `UInt8 DEFAULT 0`. У строки-дефолта: DAG создаётся,
  но **на паузе**; у поставки: TaskGroup создаётся, но **скипается**. Отличие от
  `is_active = 0`, где DAG (или таск) не создаётся вовсе.
* Колонки `schedule` и `is_recent` уходят — см. B3.

## B2. Ключи и идентификаторы в коде

* `dag_id` = `export_er__{replica}__{dag_group}`. Он же ключ верхнего уровня в Variable
  `datalab_er_wfs`: раньше группы ключевались репликой, теперь дагом, а `replica`
  и `dag_group` лежат внутри записи.
* `raw_key(row)` → `replica/dag_group/schema_name/extract_name`; у строки-дефолта —
  `replica/dag_group (дефолты группы)`. `key_to_where` разбирает обратно.
* Ключ внутри группы (`group['tables']`) — `schema_name.extract_name`: по новому ключу
  таблицы этого достаточно, реплика и группа одни на весь пакет.
* `tg` (id TaskGroup, префикс XCom, имя параметра `tbl_<tg>`) — `{schema_name}__{extract_name}`
  вместо прежнего `{db_name}__{extract_name}`. **Task_id при этом меняются**, история ранов
  по старым именам не подхватится — неизбежно, раз `db_name` уходит.
* `replica_base` / `replica_group` / `replica_full` больше не нужны: части пакета лежат
  в своих колонках. Маршрут (`TFS_MAP`) ищется по `replica` целиком, пул метки времени —
  тоже по `replica` (одна на все её группы).
* Имена файлов не меняются: архив `{replica}__{ts}__{dag_group}__{tbl}__{i}_{n}_{rows}.zip`,
  тикет `{replica}__{ts}.tkt`.
* В очередь отправки (`er_sent_files.replica`) кладём **имя пакета** `{replica}__{dag_group}` —
  ровно ту строку, что лежала там раньше. Тракт ТФС и пауза по `replicas` от этого не
  меняются вовсе: пауза «по реплике» была и остаётся паузой пакетного дага.

## B3. `schedule` и `is_recent` — в `params`

* `schedule` — ключ `params` строки-дефолта группы, и только там (см. B4).
* `is_recent` — ключ `params` поставки. Побочно чинится давняя оговорка: колонка
  `UInt8 DEFAULT 0` не позволяла отличить «не задано» от «явно delta», поэтому режим
  не наследовался вовсе. В JSON ключ либо есть, либо нет.
* Оба ключа добавляются в `GROUP_PARAMS` / `TABLE_PARAMS`.

## B4. Строка-дефолт группы, `is_active` и `is_paused`

* Строка-дефолт **обязательна**: без неё группа уходит в заглушку. У неё `extract_name`
  **и** `schema_name` пусты — ключ `(replica, dag_group, '', '')`, поэтому дефолт в группе
  физически один. Непустой `schema_name` у дефолта — ошибка настройки.
* **`schema_name` больше не наследуется** (он в ключе) и обязателен у каждой поставки.
  Список `INHERITED` пустеет и убирается: наследование остаётся только через `params`
  и `description`.
* Расписание — только из строки-дефолта; фолбэк на поставку убран. Расписание заглушки
  сломанной группы фолбэк сохраняет: иначе она перестанет краснеть в своём ритме.
* Cron проверяется `valid_schedule` — битый уронил бы разбор файла и с ним все пакеты ЕР.
* `schedule` и групповые ключи в `params` поставки — предупреждение, поставка остаётся.
* **`is_active = 0`**: у группы — DAG не создаётся (как было), у поставки — таск не создаётся.
* **`is_paused = 1`**: у группы — DAG создаётся с `is_paused_upon_creation=True`, а синк
  **дополнительно жмёт паузу** через `update_dag_pause` (`plugins/utils.py`, им же
  пользуется `ctl_worker`) — иначе на уже созданный DAG флаг не подействовал бы вовсе.
  Обратно синк паузу **не снимает**: снятую руками в UI паузу настройка возвращать не должна.
  У поставки — флаг формы `tbl_<tg>` по умолчанию снят, то есть таск штатно скипается,
  но разово включается галкой в форме запуска.
* Если **все** поставки группы на паузе, `init` не падает с «сняты флаги всех таблиц»:
  падение зарезервировано за случаем, когда флаги снял человек.

## B5. Состояние дельты — составное имя выгрузки

`export.extract_history` и `export.extract_current_vw` делит с нами xStream
(`xs_export/xs_common.py`: три INSERT и чтение по `extract_name`). Поэтому **структуру
не трогаем**: ЕР пишет и читает состояние под составным именем

    extract_name = '<dag_id>.<extract_name>'   // export_er__hrplatform_datalab__1.lc_items_meta

* `sql_cur_delta(dag_id, tbl)` фильтрует по нему же;
* `_er_save_status` пишет его в историю;
* две группы с одной таблицей автоматически ведут разные окна — их `dag_id` разные;
* xStream и его короткие имена не задеты вовсе, править `xs_common.py` не нужно.

Файл `er_export/er_extract_history.sql` остаётся, но описывает не смену структуры,
а **переименование старых строк** ЕР и способ убедиться, что чужие строки не задеты.

# Часть C. Общие настройки фреймворка — в Variable, правка из `er_setup`

## Контекст

Константы `er_config.py` (маршруты реплик, лимиты стендов, умолчания параметров, коннекты
и бакет) сейчас правятся только выкладкой. Переносим их в Variable, а форму `er_setup`
делим на две группы: **первая — общие настройки, вторая — запись `er_wf_meta`, как сейчас**.
Механика та же, что у tools-чистильщиков (`project_tools_saved_params`): код задаёт
запасной вариант, переменная — рабочий.

## C1. `er_export/er_config.py` (v1.13 → v1.14) — чтение переопределений

```python
CFG_VAR_NAME = 'datalab_er_config'
```

* `cfg_overrides() -> dict` — читает Variable через try/except (как `saved_params`
  и `known_scenarios`): недоступная или битая переменная означает «переопределений нет»
  и предупреждение в лог. Ронять разбор нельзя — это **все** пакеты ЕР разом.
* Переопределяемые ключи — явный белый список с типом из кода:

  | Ключ | Зачем |
  | :--- | :--- |
  | `TFS_MAP` | маршрут новой реплики без выкладки |
  | `LIMITS` | лимит строк по стендам |
  | `DEFAULT_PARAMS` | умолчания групповых и табличных параметров (слияние **по ключам** через `merge_params`, только известные имена) |
  | `CH_ID`, `S3_CONN`, `BUCKET` | переезд контура без выкладки |

  Всё остальное остаётся в коде: `DEF_ARGS` содержит функции; `FORMAT_MAP`, `TYPE_MAP`,
  `EXTRA_PRE/SUF`, `HIVE_RESERVED` — это формат обмена с КАП, а не настройка;
  `TS_POOL_SLOTS` обязан быть 1 по устройству пула меток времени; `POOL_SLOTS` не берём,
  потому что `ensure_pool` существующий пул не трогает — правка выглядела бы применённой,
  не будучи ею.
* Значение `null` в переменной = «вернуть значение из кода».
* Неизвестный ключ или несовпадение типа — предупреждение и игнор (а не падение);
  зато в форме `er_setup` тот же случай — ошибка, потому что там за экраном человек.

`get_config()` уже отдаёт снимок констант, а `wf_checksum` уже включает его в сумму —
значит правка общих настроек **сама** вызывает пересборку пакетов на следующем синке,
и специальных костылей не нужно. Ценой одного лишнего чтения Variable на разбор файла
(по разу в `er_export.py` и в `er_setup.py`) — тот же порядок, что у `known_scenarios`.

## C2. `er_export/er_setup.py` — форма из двух групп и таск правки

Поля формы группируются `Param(..., section=…)`: **⚙️ Общие настройки** (первой) и
**📋 Запись er_wf_meta** (существующие `record`, `patch`, `force_write`, `force_sync`).
В первой — одно поле `config_patch`: JSON только с изменяемыми ключами, `null` возвращает
значение из кода. Порядок секций в UI задаётся порядком первого появления в `params`;
если на стенде окажется иначе — оставить вторую группу без секции (поля без секции
Airflow рисует сверху) и поменять их местами.

Новый таск `config`:

* пустой патч → `AirflowSkipException` («только просмотр»), но текущее состояние всё равно
  печатается: значение из кода, переопределение, итог — по каждому ключу белого списка;
* неизвестный ключ, неверный тип, `TFS_MAP` не парой `(scenario_id, prefix)`, нецелой
  `LIMITS` → `AirflowFailException` со списком причин, переменная не трогается;
* запись — `Variable.set(..., serialize_json=True, description=f"{ts} MSK · {run_id}")`,
  как в `store_params`; итог в `add_note` и в XCom.

Место в цепочке — параллельная ветка, сливающаяся на синке:

```python
[config(), apply(check(prepare()))] >> sync()
```

Ветка именно параллельная: поставь `config()` перед `prepare()`, и штатный скип правки
конфига утянул бы в скип весь разбор записи. `sync` уже `trigger_rule='none_failed'`,
так что переживает скип обеих веток.

⚠️ **Применяется со следующего разбора файла.** Константы читаются на парсинге, поэтому
синк в этом же ране работает ещё со старым снимком и, скорее всего, уйдёт в скип по сумме.
Через ~30 секунд шедулер перечитает файл, снимок изменится, сумма разойдётся — и
следующий синк соберёт пакеты уже по новым настройкам. Это должно быть написано и в
заметке таска, и в `doc_md`, иначе выглядит как «правка не применилась».

## C3. Документация

* `doc_md` у `er_setup.py` уже печатает снимок конфига — рядом дописать, какие ключи
  переопределяемы и что сейчас переопределено.
* `er_export/README.md` — раздел «⚙️ Общие настройки»: где лежат, что можно менять,
  как вернуть значение из кода, когда правка вступает в силу.

## Проверка (C)

1. Харнесс `check_er_cfg.py` в scratchpad: слияние (пусто / известный ключ / `null` /
   неизвестный ключ / неверный тип), глубокое слияние `DEFAULT_PARAMS`, битый JSON
   переменной → значения из кода плюс предупреждение.
2. На стенде: поменять `LIMITS` и одно умолчание из `DEFAULT_PARAMS` → убедиться, что

## Чего не делаем (C)

  пересборки DAG-ов в том же процессе, чего Airflow не умеет.
