# Сироты celery в чистке метабазы и адресный реиндекс

## Why

**Правка v1.9 не удаляла того, ради чего делалась.** В v1.9 условие для `celery_taskmeta`
свели к собственному `date_done < cutoff` — и комментарий утверждал, что этого достаточно.
Неверно: `date_done` появляется **только** при переходе задачи в терминальное состояние, а
у строки, застрявшей в `STARTED` (воркер умер, не закрыв задачу), его нет никогда. Замер на
стенде 18.09.2026: дата стоит у всех 314 771 `SUCCESS` и 49 `FAILURE` и отсутствует у обеих
`STARTED`. На альфе такого осадка накопился 91 — при 94 в карточке Health, которая на него и
показывала. То есть сироты не удалялись ни разу и не удалились бы никогда.

**`REINDEX SCHEMA CONCURRENTLY` делал лишнюю работу.** Одна команда на всю схему с часовым
таймаутом и без обратной связи: проходила все индексы, включая таблицы, которых чистка не
касается. Прерывание оставляло невалидный индекс «где-то в схеме», а пропуск по правам
терялся в общем потоке notices.

**Сам реиндекс нужен редко.** Операция тяжёлая и требует админского коннекта из Vault, а
по умолчанию стояла включённой.

## What Changes

- Возраст строки `celery_taskmeta` без `date_done` определяется по `id` — он растёт вместе
  с датой; граница — максимум `id` среди уже старых строк.
- `REINDEX TABLE CONCURRENTLY` по таблицам из XCom `clean` вместо схемы целиком.
- `reindex` по умолчанию скрыт: ни параметра в форме, ни таска в графе, пока в переменной
  нет ключа. Переменная разово мигрирует по `params_version`, выкидывая только его.
- `store_params` получает аргумент `extra` для служебных ключей, которых нет в форме.

## Impact

- `check/db_cleanup.py` (v1.10), `plugins/utils.py` (общий `store_params` — им пользуются
  четыре тула), `check/readme.md`, `plugins/readme.md`.
- Тем, кто сохранял параметры до v1.10, переменная будет переписана один раз: `reindex`
  уйдёт, остальное (включая `schedule`) останется.
- Карточка Health на альфе покажет меньше сирот только после прогона чистки — сам счётчик
  правится отдельно, в etl-core.
